# S5: сверка источников расписаний (doc 59)

Проверено 2026-08-15. §4 (блокирующее к фиду) реализовано; §5 (сверка с альт-источником) — не блокирует,
требует пробного ключа; §6 (категории) операционализировано в журнал микро-live.

## §4 (БЛОКИРУЮЩЕЕ) — фид ловит пересмотры в ОБЕ стороны — реализовано

Пересмотры бывают в обе стороны (подтверждено примером Tokenomist: перенос 2026-08-13 → 2028-02-13, а также
ускоренные разлоки). Правило `55 §2.3` покрывало только перенос/отмену по открытым позициям; **ускорение
создаёт событие, которого не было** — надо ловить на входе.

Реализовано в коде (`src/main/java/org/home/data/trade`):
1. **По открытым позициям** — `ScheduleTracker.scheduleChanged` + `S5Orchestrator.maintain`: сдвиг даты или
   исчезновение → немедленное закрытие (`UNLOCK_CANCELLED`).
2. **По всей вселенной (новое, §4)** — `EventFeed.enterableWithin(today, lead)` + `S5Orchestrator.discover`:
   ловятся ВСЕ события с датой разлока в окне (today, today+5], а не только ровно unlock−5. Ускоренный
   разлок, впрыгнувший в окно (например через 2 дня), теперь попадает в кандидаты на вход через Approval
   Gate. Дедуп по открытым/ожидающим — каждое событие рассматривается один раз.

Тесты: `S5OrchestratorTest.acceleratedUnlockCaughtWithinWindow` (ловит и +5, и ускоренный +2; за окном +8 —
нет). Всего торговый слой 35/35 зелёные.

## §5.2 — определение объёма: % ЦИРКУЛИРУЮЩЕГО, не % max supply — подтверждено

Часть источников считает долю от МАКСИМАЛЬНОГО предложения; при пороге 3% это меняет состав событий
радикально. Проверено на APT: `maxSupply = 2.1e9`, а наш `circ` = сумма `documentedData.unlocked` по
категориям (total unlocked к дате) — существенно меньше maxSupply. Значит **наш фид считает `%circ =
amount / циркулирующее`** (total unlocked), что соответствует протоколу «≥3% circulating». Определение
верное, менять не нужно; при сверке с альт-источником сверять именно определение (§5.2 нижняя строка).

## §5 — сверка с альтернативным источником — НЕ блокирует, нужен пробный ключ

30 ближайших Kraken-событий DefiLlama против альтернативы (наличие/дата/объём/категория/признак
«из контракта»). Кандидаты: **Tokenomist** (бывш. TokenUnlocks, 500+ токенов, API по пробному доступу;
предпочтителен — при выборе брать источник, читающий контракты, §2.1), Messari/CryptoRank/CMC (платно/неясно).
**Отвергнуто:** биржевые виджеты (недокументированы, geo-блок, смещённая под свои листинги выборка); Binance-
календарь (ушёл из ЕС, заточен под свои листинги).

Статус: сверка требует **пробного API-ключа Tokenomist** (действие постановщика). По §7 второй фид в прод
не строим и не платим до того, как расхождения покажут необходимость. Одноразовая проверка — по готовности
ключа. Пока сверять не с чем — риск «ошибка данных vs отсутствие события» принимается как ограничение
(премия уже помечена верхней границей).

## §6 — аномалия категорий — операционализировано в журнал (диагностика, не смена протокола)

Гипотеза (§6.2): инсайдерский порядок (insider +1.11% < ecosystem +1.47%, `s5_diagnostics`) — артефакт
данных: инсайдерские разлоки чаще исполняются вручную/по соглашению → чаще пересматриваются → часть событий
не произошла в заявленную дату → премия размылась не из-за отсутствия механизма, а из-за грязных данных.

Исторических снимков расписаний нет → по §6.3 вопрос закрывается **журналом микро-live**. Реализовано:
`ScheduleTracker` теперь фиксирует **категорию получателя** с каждым пересмотром (`Revision.category`,
`revisionsByCategory()`). За первые месяцы это даст разбивку частоты пересмотров по категориям — данные,
которых нет ни у одного источника. Ожидание §9 (у insider/team пересмотров больше) записано; проверится вживую.
Это диагностика (`56 §0`): результат — в понимание механизма, не в правила торговли.
