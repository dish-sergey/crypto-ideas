# Forward-сбор тиков BTC/ETH перп — дизайн и оценка (doc 33 §D)

**Статус:** дизайн и оценка объёма готовы; **сам WS-коллектор — отдельная сборка** (по §порядку
doc 33 D наименее срочный: «запустить и забыть, ценность отложенная»). Инфраструктура-аналог
уже есть — `LiquidationWsCollector` (WS с 3 бирж, daemon-потоки, реконнект).

## D1. Что собирать (BTC и ETH перп, непрерывно, в хранилище)

| Данные | Частота | Источник |
|---|---|---|
| Лента сделок: время, цена, объём, сторона инициатора | все сделки | Kraken WS `trade` |
| Стакан L2 (10 уровней) | снимок раз в 5–10 с | Kraken WS `book` |
| Ликвидации (если отдельным потоком) | все события | WS |
| Mark / index price | раз в минуту | WS `ticker` / `kraken_ticker` |

Источник — **WebSocket**, не REST-опрос (REST-история недоступна, см. `trades_window_check.md`).

## D2. Требования

- **Только сбор, никакой аналитики** — задача не потерять данные.
- Реконнект при разрыве; **пропуски фиксировать ЯВНО** (маркер периода без данных в хранилище,
  а не «нет сделок») — то же требование, что запрет `bfill`.
- Мониторинг живости: алерт при отсутствии записей > 10 мин (по аналогии с arm-catch/litestream алертами).
- Таблицы (новые): `perp_trades(exchange,symbol,ts,price,qty,side,available_at)`,
  `perp_book(exchange,symbol,ts,bids_json,asks_json,available_at)`, `perp_mark(exchange,symbol,ts,mark,index)`.

## Оценка объёма (BTC перп, порядок величины)

- Сделки: активный BTC-перп ~десятки тысяч/сутки. При ~50k/сутки → ~18М строк/год; ×2 актива ≈ **36М/год**.
- Стакан: снимок раз в 5с = 17 280/сутки; ×2 актива ≈ **12.6М снимков/год** (по 20 уровней bid/ask в JSON).
- Mark/index 1/мин = 1440/сутки — пренебрежимо.

Итого ~50М строк/год — для SQLite на micro тяжеловато при полной ленте сделок. **Решение принято
(doc 34 §6, до запуска):** собирать **1-секундные бары с сохранением дисбаланса тейкеров**
(`buy_volume`/`sell_volume` по стороне инициатора), стакан — снимками 5–10с. Обоснование: каскад
ликвидаций длится часы, острая фаза — минуты (`t04`, `18` A7); секундного разрешения достаточно,
чтобы разметить событие и измерить дисбаланс потока. Тиковое разрешение нужно микроструктурным
задачам, которые отложены. Поля бара: `ts,symbol,open,high,low,close,buy_volume,sell_volume,trade_count,available_at`.
Пропуски фиксировать явно (период без данных ≠ период без сделок).

## D3. Зачем

Через ~1.5 года — честная тиковая история для S7, не заражённая отбором и без ревизии. Тот же
приём уже работает: `universe_snapshot` копит point-in-time вселенную с 2026-07 (`universe_bias.md`).

## Что остаётся реализовать

`KrakenPerpWsCollector` (trades + book + mark, реконнект, явные пропуски, монитор) + таблицы +
systemd-юнит на micro. Это самостоятельная сборка (аналог `LiquidationWsCollector`), не блокирует
приоритет S12 (§C4). Запускать «и забыть», как только будет решение по стеку сбора (полная лента
vs 1-сек бары).
