# crypto-ideas — слой данных торговой системы

Коллекторы бесплатных источников данных по спецификации (Google Drive
«Trading Bot — Спецификация», док. 09). Хранилище — SQLite (`data/crypto.db`),
у каждой записи время события + `available_at` для честного бэктеста.

## Быстрый старт

```bash
./gradlew test                       # юнит-тесты парсеров
./gradlew bootRun                    # постоянный режим: планировщик + WS-ликвидации
```

Разовые команды:

```bash
./gradlew bootRun --args='--collect=all'
./gradlew bootRun --args='--backfill=ohlcv --symbols=BTCUSDT,ETHUSDT --interval=1d --from=2019-01-01'
./gradlew bootRun --args='--backfill=ohlcv --symbols=BTCUSDT --interval=1m --from=2023-01-01'
./gradlew bootRun --args='--backfill=funding-okx'   # внимание: OKX хранит только ~3 мес
./gradlew bootRun --args='--backfill=onchain --from=2015-07-01'
```

Первый запуск: сначала `--backfill=...` для истории, затем постоянный `bootRun`.
Важно: OI, ликвидации и funding OKX (глубже ~3 мес) ретроспективно недоступны —
планировщик должен работать постоянно с первого дня (док. 09 §4).
Известные ограничения источников — в `CLAUDE.md`.

Настройки (символы, метрики, фиды) — `src/main/resources/application.properties`.
Подробности архитектуры — `CLAUDE.md`.

## Стенд проверки маркет-мейкинга на Revolut X

Отдельный контур в пакете `org.home.data.revx`, своя база `data/revx.db`.
Задание — `docs/63-tz-dlya-claude-code-stend-proverki.md`, план работ —
`plans/2026-08-19-revx-mm-stand.md`. Стенд **не торгует и не хранит торговых
ключей**: он собирает публичные данные и (следующим этапом) симулирует котирование.

```bash
./gradlew bootRun --args='--revx-pairs'                     # каталог пар и вселенная стенда
./gradlew bootRun --args='--revx-probe-limits'              # эмпирический потолок запросов
./gradlew bootRun --args='--revx-collect=once'              # разовый обход книг и сделок
./gradlew bootRun --args='--revx-collect'                   # непрерывный сбор (демон)
./gradlew bootRun --args='--revx-basis --hours=6'           # курс USDC/USD и пригодность пар
```

### Оговорки, без которых числа стенда нельзя читать

- **maker 0% — вероятно промо** молодой площадки. Конструкция, нежизнеспособная
  при maker 0.02%, держится на акции, а не на преимуществе. Прогон чувствительности
  к комиссии — основной, а не дополнительный.
- **Спот-онли означает вынужденный лонг**: аск можно котировать только в пределах
  имеющегося инвентаря, поэтому корректный бенчмарк — держание инвентаря, а не ноль.
- **Симуляция не отвечает на вопрос о внутреннем матчинге.** Если широкий спред на
  USDC-книге держит сама биржа, поток может не доходить до наших заявок. Это
  разрешается только живыми заявками минимального размера.
- **Выводы ограничены собранным периодом**; неделя данных не описывает стресс.

### Отклонения от ТЗ, вынужденные измерениями площадки

| ТЗ | Реальность | Следствие |
|---|---|---|
| Python + parquet | Java + SQLite | стек проекта; экспорт в CSV/parquet — по необходимости |
| 20 пар с опросом раз в 5 с (§3.4) | **выполняется** — с ключом API (1000 req/мин) | все 23 пары каждые 5 с; без ключа падаем на ярусы (ETH/BTC — 10 с, хвост — 10 мин) |
| Ноги пары одновременно, skew < 250 мс (§3.3) | **выполняется** — залпом по авторизованному пути | измерено: skew в среднем 4.8 мс, максимум 93 мс (2600 снимков). Публично было 1250 мс |
| Определение агрессора по близости к биду/аску (§4.3) | API отдаёт `side`, и документация называет это стороной **агрессора** | поле пишется как есть, правило ТЗ остаётся валидатором на чтении |

Ключ выпущен **только на чтение** — стенд по-прежнему не может отправить ордер.
Без ключа приложение не падает, а переходит на публичные эндпоинты с их 1 req/s.

### Первое наблюдение, которое меняет чтение док. 62

19.08.2026, на движении ETH в 18%: спред опорной книги **ETH/USD раздвинулся до
1.18%** против 0.016% у BTC/USD, а подразумеваемый курс USDC/USD по ETH ушёл на
−3.5% при том, что остальные 22 пары дали 0.9999 с разбросом в сотые доли процента.
То есть опорная книга надёжна **не всегда**, и именно в момент сильного движения.
Проверка разброса из ТЗ §4.1 — не формальность, а главный предохранитель
стратегии: без неё котирование пошло бы от цены, промахнувшейся на 3.5%.

## Счётные стенды теории оптимальности (ТЗ docs/65–68)

Пакет `org.home.data.theory`, своя база `data/theory.db`. Стенды **ничего не
торгуют и не трогают конфигурацию идущего микро-live S5** (правило одного
изменения): это оффлайн-расчёты на уже собранных данных.

```bash
./gradlew bootRun --args='--theory=s5-import'                   # датасет событий S5 (разово, ходит в сеть)
./gradlew bootRun --args='--theory=alloc --out=reports/theory'  # ТЗ 65: аллокатор поверх пула S1–S12
./gradlew bootRun --args='--theory=kelly --out=reports/theory'  # ТЗ 66: размер позиции S5
./gradlew bootRun --args='--theory=ou --out=reports/theory'     # ТЗ 67: допуск OU (предтест блока B)
./gradlew bootRun --args='--theory=band --out=reports/theory'   # ТЗ 68: полоса и разорение
./gradlew bootRun --args='--theory=verify --out=reports/theory' # ТЗ 72: доверификация + сверка констант S5
```

**Выбор стека** (ТЗ §2 требует зафиксировать одной строкой): Java 25 + Gradle —
стек проекта; встраиваемая БД прогонов — SQLite (та же, что у слоя данных);
parquet для рядов пишется встраиваемым **DuckDB** (`org.duckdb:duckdb_jdbc`) —
один джарник вместо `parquet-avro`, тянущего за собой Hadoop, и те же файлы
потом читаются SQL-ом без внешнего сервера.

Каждый прогон пишет в `theory_run` git-хэш (с суффиксом `-dirty` на
незакоммиченном дереве), полный конфиг, диапазон данных, seed и результат —
**без этой записи прогон недействителен**.

### Оговорки, без которых числа стенда 65 нельзя читать

- **Граница регрета относительна.** `O(√(T·ln N))` гарантирует «не сильно хуже
  лучшей стратегии пула» и ничего не обещает про прибыль: пул из убыточных
  стратегий даёт убыточный портфель при полном соблюдении гарантии.
- **Результат — верхняя граница, а не оценка.** Все кривые пула, кроме ставки
  кэша, помечены `in_sample`: параметры стратегий выбраны со знанием истории
  проекта, и аллокатор наследует это смещение целиком.
- **Кривая S2S9 завышена**: PIT-снимков капитализаций в базе нет (док. 09 §4.3),
  вселенная — сегодняшний список символов, то есть survivorship.
- **Кривая S7 — дневное приближение**: внутридневного контура у проекта нет.
- **S12 в пул не вошла** — не по результату, а из-за данных: PIT-funding по 833
  перпам доступен только с живого fapi. Это записано в конфиге до прогона.
- **η не подбирается**: берётся теоретическое `η* = √(8 ln N / T) / G`, где `G` —
  наблюдённый размах дневных доходностей пула. Тем же `G` масштабируется граница
  регрета, поэтому η и граница согласованы; всё остальное — только сетка
  чувствительности.
- **Издержки оборота внутри стратегии уже вычтены из её кривой** и повторно не
  списываются: движок берёт только издержки переключения весов между стратегиями.

### Что показали прогоны стендов (кратко; полные отчёты — `reports/theory/`)

| Стенд | Главный результат |
|---|---|
| ТЗ 65, аллокатор | Верхний ориентир `BEST_FIXED` бьёт SMA200 (99.7% против 36.8% CAGR), **но на 90% состоит из одной кривой — S2S9 с survivorship-вселенной**. `HEDGE` укладывается в теоретическую границу регрета, обходит `EW` и стоит на 66-м процентиле случайных постоянных миксов, но при удалении S2S9 его CAGR падает с 24.6% до 4.3% → работает не аллокатор, а одна кривая |
| ТЗ 66, сайзинг S5 | Точечный Kelly даёт 102% на событие, нижняя граница бутстрапа — 44%: **это не рекомендация, а демонстрация того, что Kelly на одиночном событии не учитывает кластеризацию**.
