# Исполнитель: где живёт, как управляется, как выпустить ключ

Спецификация перед реализацией. Отвечает на три вопроса: куда деплоим на ARM,
как устроен управляющий Telegram-бот и как выпустить торговый ключ.

---

## 1. Почему именно ARM и именно там

Исполнитель обязан читать справедливую цену **из базы стенда** — иначе расхождение
по исполнениям можно будет списать на разные данные, и всё измерение потеряет
смысл (док. 89 §4). База лежит на ARM, значит и исполнитель живёт на ARM.
Вариантов размещения фактически нет.

Раскладка:

```
~/revx/                      стенд, НЕ ТРОГАЕМ
   app.jar                   коллектор
   data/revx.db              исполнитель открывает ТОЛЬКО НА ЧТЕНИЕ (mode=ro)
   keys/                     ключ на чтение (тот, что уже есть)

~/revx-exec/                 исполнитель
   app.jar                   СВОЯ КОПИЯ того же jar, не симлинк
   state/exec.db             журнал запросов и ответов, свои сделки
   logs/

/etc/revx-exec.env           торговый ключ + токен бота, 600 root
/etc/systemd/system/revx-exec.service
```

**Почему отдельная копия jar, а не симлинк.** Обновление коллектора не должно
молча менять код исполнителя, и наоборот. Атомарный `mv` одного файла тогда
затрагивает только своего владельца. Стоит 99 МБ — при 40 ГБ свободных это ничто.

**Почему база открывается на чтение.** `mode=ro` в JDBC-строке — гарантия на
уровне драйвера, что исполнитель физически не может испортить невосполнимые
данные стенда. Разделение из ТЗ §0 держится не на дисциплине, а на флаге.

**Мелочь, о которой забудешь через месяц:** spring-бин `Db` создаёт `data/crypto.db`
при любом старте приложения. В `~/revx-exec/` появится пустой файл — это мусор,
а не ошибка (так же ведёт себя `~/revx/`).

## 2. Управляющий Telegram-бот

**Бот обязан быть НОВЫЙ, не S5.** Два потребителя `getUpdates` на одном токене
дают 409, и живой торговый слушатель S5 сломается. Это уже записано в
`deploy/SERVERS.md` как грабля — второй раз наступать не будем.

### Команды

| Команда | Что делает |
|---|---|
| `/status` | работает или остановлен, текущие котировки, инвентарь, открытые заявки, аптайм, последнее исполнение |
| `/stats` | исполнений за сутки против предсказанных **104**, доля «разобрали» против предсказанных **6.0%**, израсходовано постановок из 1000 |
| `/stop` | снять все заявки и перестать котировать; процесс жив |
| `/start` | возобновить котирование |
| `/panic` | снять все заявки и **выйти из процесса** |
| `/limits` | показать жёсткие лимиты (только показать) |
| `/help` | список команд |

### Четыре правила безопасности, без которых бот опаснее пользы

**1. Бот не может менять параметры — только останавливать и запускать.** Ни
размера, ни отступа, ни лимита экспозиции. Всё это остаётся в коде и конфиге.
Иначе доступ к чату превращается в доступ к деньгам.

**2. По умолчанию процесс стартует ОСТАНОВЛЕННЫМ.** Котирование начинается только
после явной `/start`. Смысл: перезапуск по `Restart=` после падения не должен сам
собой возобновлять торговлю — сначала человек смотрит, почему упало.

**3. Слушатель — на отдельном потоке.** `/panic` обязана срабатывать, даже если
цикл котирования заклинил. Иначе аварийная остановка есть только на бумаге.

**4. Чужой чат игнорируется молча** — сверка `chat_id`, как в S5
(`TelegramCommandListener:91`). Ответов на неизвестные чаты нет вообще.

### Как завести бота

1. В Telegram написать `@BotFather` → `/newbot` → имя и username.
2. BotFather выдаст токен вида `123456789:AA...`.
3. Написать новому боту любое сообщение (иначе он не сможет писать первым).
4. Узнать `chat_id`: `curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates"`
   и взять `message.chat.id`.
5. Токен и chat_id — в `/etc/revx-exec.env`, в git не попадают.

## 3. Торговый ключ Revolut X

Тот же механизм, что у ключа на чтение (Ed25519), но с правом торговли.

### Шаг 1: сгенерировать пару НА ARM

Приватный ключ не должен никуда ехать — генерируем там, где он будет жить:

```bash
ssh -i ~/.ssh/armkey ubuntu@130.61.31.216
mkdir -p ~/revx-exec/keys && chmod 700 ~/revx-exec/keys
cd ~/revx-exec/keys
openssl genpkey -algorithm ed25519 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem
chmod 600 private.pem
cat public.pem          # ЭТО вставляется в веб-приложение
```

### Шаг 2: зарегистрировать публичный ключ

В веб-приложении Revolut X, в разделе API-ключей:

- вставить содержимое `public.pem` целиком, вместе со строками
  `-----BEGIN PUBLIC KEY-----` и `-----END PUBLIC KEY-----`;
- **права: торговля** (у прежнего ключа было только чтение — в этом вся разница);
- **IP-whitelist: `130.61.31.216`**.

### Про IP — почему именно этот

Это публичный адрес bot-arm, и он же **фактический исходящий** — проверено
только что: `curl https://api.ipify.org` с ARM отвечает `130.61.31.216`. Тот же
адрес стоит в whitelist ключа на чтение, и тот работает.

Если когда-нибудь запускать исполнитель с micro, адрес будет другой
(`89.168.115.160`), но запускать его оттуда нельзя: база стенда лежит на ARM.

### Шаг 3: положить ключ туда, где его возьмёт systemd

Площадка выдаст 64-символьный API-ключ. По ТЗ §6 торговые ключи идут **через
переменные окружения**, а не из конфига приложения:

```bash
sudo tee /etc/revx-exec.env >/dev/null <<'EOF'
REVX_TRADE_KEY=<64 символа от Revolut X>
REVX_TRADE_SECRET_B64=<base64 приватного ключа, см. ниже>
REVX_BOT_TOKEN=<токен от BotFather>
REVX_BOT_CHAT=<chat_id>
EOF
sudo chmod 600 /etc/revx-exec.env
sudo chown root:root /etc/revx-exec.env
```

Приватный ключ в одну строку:

```bash
base64 -w0 ~/revx-exec/keys/private.pem
```

После этого `~/revx-exec/keys/private.pem` **удалить** — он останется только в
root-овом env-файле, как ключи B2 в `/etc/litestream.env` на micro. Это та же
схема, что уже используется в проекте, и она же удовлетворяет ТЗ §6.

### Чего делать нельзя

- не выпускать ключ с правом **вывода средств** — торговли достаточно;
- не класть ключ в `~/revx-exec/` рядом с jar: там его увидит любой процесс
  пользователя `ubuntu`;
- не переиспользовать ключ стенда — у него нет торговых прав, и смешивать роли
  нельзя даже если бы были.

## 4. Порядок

| # | Шаг | Кто |
|---|---|---|
| 1 | Бот у BotFather, узнать chat_id | ты |
| 2 | Сгенерировать пару на ARM, зарегистрировать публичный ключ с правом торговли и IP `130.61.31.216` | ты (команды — §3) |
| 3 | Положить на счёт Revolut X по ~$10 в BTC и USDC | ты |
| 4 | Заполнить `/etc/revx-exec.env` | ты или я по твоим значениям |
| 5 | Проверка `post_only` одной пересекающей заявкой | я |
| 6 | Исполнитель + бот + systemd-юнит | я |
| 7 | Микро-live двумя размерами, сверка с предсказаниями | я |

Шаги 1–3 — твои, дальше моё. Шаг 5 стоит перед 6: если `post_only` площадка не
поддерживает, исполнителю нужен ценовой предохранитель вместо флага, и знать это
надо до, а не после написания цикла.
