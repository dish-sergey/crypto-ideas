## Блок A. Внедрить детектор v5

### A1. Заменить конструкцию

```
close > SMA200(close)  →  BULL
close ≤ SMA200(close)  →  BEAR
```

Ноль параметров. **Гистерезиса нет, dwell-lock нет** — это сознательно, не забытая деталь.

Прогрев 200 дней, прогретые дни в оценку не входят и ничем не заполняются.

### A2. Удалить

- состояния `RANGE`, `TRANSITION`, `CRASH`;
- оси `D`, `T`, `S` и всё, что их считает;
- `dd_speed` (любые вхождения);
- dwell-time lock и его таймер;
- соответствующие строки из `ALLOCATION_MATRIX`.

### A3. Матрица аллокации — две строки

Из `00-obzor-arhitektura-v2.md` §4:

| Стратегия | BULL | BEAR |
|---|---|---|
| S1 funding-arb | 50% | 30%* |
| S2 momentum | 35% | 0% |
| S3 mean-rev | 0% | 0% |
| S4 стейблы + yield | 5% | 55% |

| S6 лестница | 0% | 0–15%** |
| Резерв | 10% | 5% |

\* только при положительном скользящем funding, иначе капитал в S4
\** только при `cycle_phase = ACCUMULATION`, забирает из S4

### A4. Гейты стратегий

| Стратегия | Гейт |
|---|---|
| S1 | `state ≠ BULL` для повышенного веса; работает всегда при положительном funding |
| S2 | `state = BULL` **и** `breadth ≥ 0.35` |
| S3 | **не активна**, капитал 0 |
| S4 | `state = BEAR` основной вес |
| S5 | `state = BEAR` |
| S6 | `state = BEAR` **и** `cycle_phase = ACCUMULATION` |

**Условие `confidence ≥ 0.4` у S2 удалить** — величина не валидирована.

### A5. Модификаторы

`cycle_phase`, `macro_flag`, `breadth`, `leverage_warning` — вычисляются, состояние не меняют.

`stress_level` — вычисляется и логируется, **на решения не влияет**, флаг `stress_level_is_diagnostic: true`.

### A6. Confidence

Формула из `01-detektor-rezhima-v5.md` §3, помечена как непроверенная эвристика.

**Запрещено использовать confidence для расчёта размера капитала** (`03-risk-management-v2.md` §2).

### A7. Выходной контракт

```json
{
```

### A8. Проверки

1. **Causality:** для 20 случайных дат предсказание на усечённых данных совпадает с предсказанием на полных.
2. **Воспроизведение эталона:** BTC 2020-01-01 … 2026-07-23, прокси из стенда → `CAGR ≈ 36.7%`, `MaxDD ≈ −53.7%`. Расхождение больше 0.5 п.п. — искать ошибку.
3. **Потребители удалённых полей:** найти всё, что читает `axes`, `RANGE`, `TRANSITION`, `CRASH`; переключить либо удалить. Молчаливый обвал на отсутствующем ключе недопустим.
4. **Гистерезис отсутствует:** минимальная длительность состояния может быть 1 день.

## Блок E. Деривативные данные и `leverage_warning`

Новое в v2. Выполнять **до или параллельно с блоком D** — данные нужны для S1 в любом случае.

### E1. Мотивация

`leverage_warning` описан в детекторе с версии v2 и присутствует в v5, но **ни разу не вычислялся**: деривативные данные в стенде не подключались вовсе (`15-…-v5.md` §2). Вопрос «несёт ли накопленное плечо информацию» формально **открыт**, а не отвечен отрицательно.

Сборщик всё равно нужен для S1 (funding-арбитраж) — там те же данные. Задача сводится к тому, чтобы **сразу складывать историю, а не только текущие значения**.

### E2. Что собирать

| Данные | Частота | Источник | Глубина |
|---|---|---|---|
| Funding rate | каждые 8 часов | биржевой API | вся доступная (Binance с 2019-09, BitMEX с 2016) |
| Open Interest | ежедневно, закрытие | биржевой API | вся доступная |
| Market Cap | ежедневно | CoinGecko/CMC | вся доступная |

Инструменты на первом этапе: BTC, ETH. Позже расширяется до вселенной S12.

**Ключевое требование: складывать в хранилище, а не запрашивать по требованию.** Funding задним числом не пересматривается (в отличие от on-chain), но API-доступ к истории может исчезнуть или стать платным.

### E3. Вычислить `leverage_warning`

```
oi_growth       = рост (OI / MarketCap) за 14 дней при неположительном изменении цены
funding_persist = funding по BTC+ETH выше 0.05%/8ч непрерывно ≥ 7 дней

leverage_warning = oi_growth ≥ 20%  ИЛИ  funding_persist
```

Считать на всю доступную историю, сохранять как ряд, а не только текущее значение.

### E4. Описательное исследование (doc 23 §5.1)

**Событийная выборка** — пять крупных обвалов:

| Событие | Ориентировочный период |
|---|---|
| Медвежий 2018 | январь 2018 |
| Ковид | март 2020 |
| Май 2021 | май 2021 |
| Ноябрь 2021 – май 2022 | ноябрь 2021 |
| Август 2024 | август 2024 |

**Контрольная выборка:** пять случайно выбранных спокойных периодов той же длины, где за последующие 30 дней просадка не превысила 15%. Выбор случайный, с фиксированным зерном генератора, записанным в отчёт.

**Что посчитать** для каждого периода за 30, 14 и 7 дней до точки:

- `oi_growth`
- `funding_persist` (число дней подряд)
- `vol_calm` — процентиль реализованной волатильности 30д в окне 2 года
- `cycle_phase`

**Форма отчёта:** таблица «событие × метрика × горизонт», рядом та же таблица для контрольных периодов.

### E5. Как читать результат — критично

**Это описательное исследование, а не доказательство.** Пять событий статистики не дают (`t07`, `23` §2.1). Отчёт обязан содержать эту оговорку в первой строке.

Вопрос, на который оно отвечает: **отличались ли метрики перед обвалами от спокойных периодов.** Не «предсказывают ли они обвалы».

| Исход | Решение |
|---|---|
| Метрики перед обвалами неотличимы от контрольных | компоненты убираются из индикатора хрупкости (`23` §4.3), остаётся базовое транширование |
| Различались во всех пяти случаях | основание пользоваться как грубым ориентиром для темпа ввода капитала, **не как торговым сигналом** |
| Различались в части случаев | зафиксировать как есть, в индикаторе оставить, вес не подбирать |

**Что запрещено:**

- **Подбирать пороги** (20%, 0.05%, 7 дней) по результатам. Они заданы в спецификации детектора до всякого измерения.
- **Превращать в торговый сигнал.** Хрупкость как основание сокращать позицию отвергнута дважды и числится в `rejected.md` (состояние `CRASH`, volatility targeting). Настоящее исследование обслуживает только протокол ввода капитала.
- **Расширять событийную выборку** «похожими» просадками, чтобы получить больше точек. Пять событий — это пять событий.

Отчёт: `reports/leverage_warning_study.md`. Записи в журнал гипотез — до прогона.

## Блок D. Кросс-секция, фаза 1

Основная работа. Спецификация — `17-tz-kross-sekcionnyj-stend-v3.md`.

### D1. Порядок неизменен

```
вселенная point-in-time
  → движок с издержками
  → равновзвешенная корзина + BTC B&H
  → только потом S2 с измерением IC
```

**Правило «тривиальный бенчмарк первым»** (`15-…-v5.md` §4.1). Корзина считается **до** реализации S2. Это тот урок, который стоил детекторного направления: SMA200 надо было прогнать первым, а прогнали последним после четырёх версий композита.

### D2. Вселенная point-in-time — блокирующая задача

`universe(date) -> list[symbol]`, состав **на ту дату**, без знания будущего.

Фильтры (`17` §3.4): исключить стейблкоины, обёрнутые токены (WBTC, stETH и аналоги), токены младше 60 дней с первой свечи; порог ликвидности по медианному обороту за 30 дней.

**Делистинг обрабатывается явно:** позиция закрывается по последней доступной цене. Молчаливое исчезновение из данных — скрытая утечка, при которой убыток не попадает в результат.

### D3. Измерить смещение выживаемости

```
1. Вселенная наивно: сегодняшний топ-100, прогнать назад
2. Вселенная корректно: point-in-time
3. Прогнать одну и ту же стратегию на обеих
4. Разница в CAGR — цена ошибки
```

Отчёт: `reports/universe_bias.md`.

### D4. Чего не делать

**Не запускать на сегодняшнем топ-100 «пока, для предварительной оценки».** Такой прогон не даёт предварительного результата — он даёт дезинформацию: мёртвые монеты в выборку не попадают, и результат выходит великолепным и полностью фальшивым.

## Общие правила

- **Параметры фиксируются в конфиге до прогона.** Захардкоженное число в коде — дефект.
- **Журнал гипотез append-only.** Каждый прогон — запись, включая отброшенные и отладочные.
- **Отвергнутое не возвращается** без нового измерения, опровергающего основание (`rejected.md`, `00-index-i-status-v3.md` §3).
- **Не перекалибровывать ничего** «раз уж всё равно переделываем».
