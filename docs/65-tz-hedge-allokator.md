# ТЗ для Claude Code: регрет-минимизирующий аллокатор поверх пула стратегий

**Позиции каталога:** E1 (S30) + E4 (M-alloc-bench), док. `64` §Блок E.

**Что строим.** Оффлайн-стенд, который берёт исторические кривые доходности стратегий S1–S12, прогоняет по ним несколько алгоритмов распределения капитала и отвечает на один вопрос: **сколько вообще стоит любая аллокация поверх этого пула**.

**Что НЕ строим.** Ничего живого. Ни подключения к биржам, ни ордеров, ни ключей. Это счётный стенд на существующих данных.

---

## 0. Главное предупреждение исполнителю

**Аллокатор поверх исторических кривых почти всегда выглядит лучше, чем он есть.** Четыре причины, и все должны быть явно обработаны:

1. **Look-ahead второго порядка.** Кривые стратегий сами получены бэктестом, в котором параметры стратегий уже выбраны с знанием всей истории. Аллокатор, работающий поверх таких кривых, наследует это смещение целиком. Оно не устраняется — оно **декларируется**, и результат интерпретируется как верхняя граница, а не как оценка.
2. **Survivorship внутри пула.** В пуле лежат стратегии, которые дошли до стадии «есть кривая». Те, что были отброшены раньше, кривой не имеют и в пул не попали.
3. **Доступность.** S1 активна 17% времени, S5 событийная, S6 гейтится фазой цикла. Аллокатор **не может** отдать капитал стратегии, которой в этот момент нет. Наивная реализация, распределяющая веса по всем N стратегиям всегда, даст фантомный результат.
4. **Издержки переключения.** Базовая граница регрета Hedge их не содержит. Ежедневная перекладка весов при 0.16–0.20% round-trip съедает больше, чем даёт.

**Главная ловушка интерпретации.** Граница регрета `O(√(T·ln N))` — **относительная**. Она гарантирует лишь, что вы не сильно хуже лучшей стратегии пула. Если весь пул убыточен, гарантия выполняется и результат при этом отрицательный. Формулировка «алгоритм работает» здесь ничего не значит без абсолютного бенчмарка.

**Если стенд покажет, что Hedge бьёт SMA200 — первая гипотеза должна быть «ошибка в маске доступности или в издержках», а не «нашли аллокатор».**

**Гипотеза, которую проверяет стенд.** Распределение капитала между стратегиями алгоритмом с доказанной границей регрета даёт результат не хуже, чем матрица аллокации по режимам детектора, и не требует детектора вообще.

**Записанное заранее ожидание.** Hedge покажет результат между медианной и лучшей стратегией пула и **не превзойдёт SMA200 buy & hold**. Записано до постройки.

**Почему стенд всё равно нужен при таком ожидании.** Он даёт величину, которой сейчас нет: результат **лучшего постоянного микса, выбранного задним числом**. Это недостижимый верхний ориентир. Если он не бьёт SMA200 — значит никакой аллокатор, ни детектор, ни Hedge, ни идеальный оракул, не мог бы. Тогда вопрос об аллокации поверх этого пула закрывается целиком, а не по одной гипотезе за раз.

## 2. Стек и общие требования

**Язык — Java.** Версия, сборщик и библиотеки — на усмотрение исполнителя; сделанный выбор фиксируется в `README.md` одной строкой с обоснованием. Это **переопределяет док. `63` §2**, где указан Python: старые ТЗ на Python не переписываются, новые пишутся на Java.

Требования, не зависящие от выбора библиотек:

- Хранилище: встраиваемая БД для метаданных прогонов + колоночный формат (parquet) для рядов. Никакого внешнего сервера.
- Конфигурация — **один файл конфигурации**. Все параметры стратегии, издержек и порогов — только оттуда, никаких констант в коде.
- Время — **UTC, миллисекунды, целые числа** (`long`). Ни одного значения времени без явной зоны.
- Логирование структурное (JSON-строки), уровень настраивается.
- Автотесты обязательны и покрывают §7 целиком.
- `README.md` с командами сборки и запуска каждого модуля.

**Воспроизводимость.** Каждый прогон пишет запись: git-хэш, полный конфиг, диапазон данных, версия алгоритма, seed, результат. Повторный прогон на тех же данных с тем же конфигом даёт **побитово тот же** результат.

## 3. Модуль 1: слой данных

### 3.1 Единый формат кривой стратегии

Каждая стратегия приводится к таблице с дневным шагом:

| Поле | Тип | Смысл |
|---|---|---|
| `date` | int, UTC ms | торговый день |
| `strategy_id` | str | `S1`, `S2`, … |
| `ret` | float | доходность **одного доллара, отданного этой стратегии в этот день** |
| `available` | bool | стратегия могла принять капитал в этот день |
| `turnover` | float | оборот стратегии за день, доля от её капитала |
| `curve_kind` | enum | `walk_forward` / `in_sample` / `live` |

**`ret` определяется на задействованный капитал, а не на общий.** Это принципиально: стратегия, активная 17% времени, при определении «на общий капитал» будет выглядеть как стратегия с околонулевой доходностью и малой волатильностью, и аллокатор ошибочно даст ей большой вес.

### 3.2 Маска доступности — критическое требование

**`available = false` означает, что капитал, назначенный этой стратегии, лежит в кэше.** Реализация:

```
r_portfolio(t) = Σ_i w_i(t) · [ available_i(t) ? ret_i(t) : rate_cash(t) ]
```

Веса нормируются по **всем** стратегиям, включая недоступные. Альтернативная нормировка (только по доступным) — тоже допустимый режим, но это **другая** стратегия аллокации, и она считается отдельным прогоном, а не вариантом реализации.

`rate_cash` берётся из конфига по датам. **Не константа 8%** — док. `01 v5` §6.4 прямо указывает, что это завышение. Использовать фактическую достижимую ставку по датам.

### 3.3 Честность источника кривой

Поле `curve_kind` обязательно и обязательно попадает в отчёт.

| Значение | Как трактуется в отчёте |
|---|---|
| `in_sample` | результат аллокатора — **верхняя граница**, не оценка. Помечается в каждой таблице |
| `walk_forward` | результат интерпретируется как оценка |
| `live` | приоритетный источник |

**Если хотя бы одна кривая помечена `in_sample`, весь отчёт помечается как верхняя граница.** Это не портит ценность стенда: главный вопрос §1 («бьёт ли верхний ориентир SMA200») именно на верхней границе и решается.

### 3.4 Бенчмарки

Загружаются тем же слоем и в том же формате:

| ID | Что |
|---|---|
| `BH_BTC` | buy & hold BTC |
| `BH_ETH` | buy & hold ETH |
| `SMA200` | переключение BTC/кэш по SMA200 |
| `CASH` | ставка кэша по датам |
| `EW_POOL` | равные веса по доступным стратегиям пула |

`SMA200` — главный бенчмарк, потому что именно его не превзошёл детектор.

## 4. Модуль 2: аллокаторы

Все аллокаторы реализуют один интерфейс: на вход история доходностей и доступности **до дня `t` включительно**, на выход веса на день `t+1`. Использование данных дня `t+1` и позже — дефект.

### 4.1 Обязательный набор

| ID | Алгоритм | Роль |
|---|---|---|
| `EW` | равные веса по доступным | тривиальный бенчмарк, **считается первым** |
| `DETECTOR` | матрица аллокации по состояниям детектора | то, что используется сейчас |
| `HEDGE` | мультипликативные веса: `w_i ∝ exp(η · Σ_s≤t ret_i(s))` | основной кандидат |
| `EG` | Exponentiated Gradient (Helmbold et al.) | вариант с градиентом по доходности портфеля |
| `ONS` | Online Newton Step | регрет `O(log T)` |
| `BEST_FIXED` | лучший постоянный микс **задним числом** | недостижимый верхний ориентир |
| `BEST_SINGLE` | лучшая одиночная стратегия задним числом | база для расчёта регрета |
| `RANDOM` | случайные веса из симплекса, фиксированный seed | контроль |

**`BEST_FIXED` и `BEST_SINGLE` смотрят в будущее намеренно.** Это ориентиры, а не стратегии. В отчёте они всегда в отдельной секции с явной пометкой.

**`RANDOM` обязателен.** Он отвечает на вопрос, добавляет ли ценность **выбор весов** или работает сам факт диверсификации. Аллокатор, не превосходящий случайные веса, отклоняется — это тот же приём, что «случайное исключение токенов» в задании `Z2` (док. `60` §7).

### 4.2 Издержки переключения

```
cost(t) = c_switch · Σ_i |w_i(t) − w_i(t−1)| / 2
```

`c_switch` — из конфига, прогоняется по сетке (см. §5). Коэффициент `1/2` потому, что `Σ|Δw|` считает и продажу, и покупку.

Дополнительно к переключению весов учитывается **собственный оборот стратегии**: `turnover_i(t)` уже отражён в `ret_i`, повторно не списывается. Это надо явно проверить при загрузке данных и записать в README, иначе издержки будут посчитаны дважды.

### 4.3 Инерционный вариант

`HEDGE_LAZY` — версия с издержками переключения в постановке (Блум–Калаи): веса пересматриваются, только если выигрыш от пересмотра превышает его стоимость. Реализуется как порог на `Σ|Δw|`.

**Порог задаётся из логики, а не подбирается по результату.** Естественный кандидат: порог, при котором ожидаемая экономия издержек равна ожидаемой потере от устаревших весов. Если такой вывод сделать не удаётся, порог берётся из сетки чувствительности и это фиксируется как ограничение.

## 5. Обязательные прогоны

| Прогон | Сетка |
|---|---|
| **Базовый** | `HEDGE` с `η` из конфига, `c_switch` = 0.15% |
| Чувствительность к `η` | `η` ∈ {0.5, 1, 2, 5, 10} × теоретическое `η* = √(8 ln N / T)` |
| Чувствительность к издержкам | `c_switch` ∈ {0%, 0.05%, 0.10%, 0.20%, 0.50%} |
| Чувствительность к окну | скользящее окно накопленного P&L ∈ {без окна, 90, 180, 365 дней} |
| Нормировка весов | по всем стратегиям / только по доступным |
| Подпериоды | по годам и по режиму SMA200 (BULL/BEAR) отдельно |
| Устойчивость к составу пула | **leave-one-out**: убрать по одной стратегии, пересчитать |
| Издержки ×1.5 | пессимистичный прогон |

**Leave-one-out обязателен.** Он отвечает на вопрос, держится ли результат на одной стратегии. Если удаление S5 (единственной работающей) обрушивает всё — аллокатор не нашёл ничего, он просто нашёл S5, и тогда честный вывод «держите S5», а не «внедряйте аллокатор».

## 6. Модуль 3: отчёт

Один markdown-файл плюс parquet с сырыми результатами.

### 6.1 Раздел «Данные»

Период, число стратегий, доля дней с `available = true` по каждой стратегии, распределение `curve_kind`, использованная ставка кэша по годам, число пропусков.

**Если хотя бы одна кривая `in_sample` — шапка отчёта содержит явную строку: «Результаты — верхняя граница, не оценка».**

### 6.2 Раздел «Аллокаторы»

По каждому алгоритму и каждому прогону:

| Метрика |
|---|
| CAGR, волатильность, Sharpe, дефлированный Sharpe с честным `N` прогонов |
| Максимальная просадка и её дата |
| Реализованный регрет против `BEST_SINGLE` и против `BEST_FIXED` |
| **Теоретическая граница регрета** для того же `T` и `N` |
| Средний `Σ|Δw|` в день; суммарные издержки переключения |
| Доля капитала в кэше по времени |
| Разбивка вклада по стратегиям: сколько P&L пришло от каждой |

### 6.3 Раздел «Вердикт»

Прямые ответы:

1. Превосходит ли `BEST_FIXED` (недостижимый ориентир) SMA200? **Если нет — вопрос об аллокации поверх этого пула закрыт целиком.**
2. Превосходит ли `HEDGE` матрицу `DETECTOR`? На сколько п.п.?
3. Превосходит ли `HEDGE` равные веса `EW`?
4. Превосходит ли `HEDGE` случайные веса `RANDOM`?
5. При какой `c_switch` преимущество `HEDGE` обращается в ноль?
6. Укладывается ли реализованный регрет в теоретическую границу?
7. Сохраняется ли результат при удалении S5? При удалении любой одной стратегии?
8. Сосредоточен ли вклад в одном годе?

### 6.4 Kill-критерии

Сформулированы **до** первого прогона.

| Условие | Вывод |
|---|---|
| `BEST_FIXED` не превосходит SMA200 | **аллокация поверх пула бессмысленна в принципе.** Направление закрывается, детектор как аллокатор тоже — но это уже известно |
| `HEDGE` не превосходит `EW` | алгоритм не добавляет ценности сверх диверсификации |
| `HEDGE` не превосходит `RANDOM` | выбор весов не добавляет ценности |
| Преимущество исчезает при `c_switch` = 0.15% | конструкция нежизнеспособна при фактических тарифах |
| Преимущество исчезает при удалении одной стратегии | работала эта стратегия, а не аллокатор |
| Реализованный регрет превышает теоретическую границу | **дефект реализации**, а не результат. Прогон недействителен |

## 7. Тесты — критерии приёмки

Без этих тестов работа не принимается.

### 7.1 Корректность алгоритмов — синтетика с известным ответом

| Сценарий | Ожидаемое поведение |
|---|---|
| Одна стратегия строго доминирует, остальные — ноль | `HEDGE` сходится к ней; реализованный регрет **не превышает** теоретическую границу |
| Все стратегии — независимый шум с нулевым средним | `HEDGE` ≈ `EW`, веса не расходятся |
| Две стратегии чередуются блоками по режимам | `HEDGE` отстаёт от `BEST_SINGLE`, но укладывается в границу; `BEST_FIXED` бьёт обе одиночные |
| Все стратегии убыточны одинаково | `HEDGE` убыточен так же. **Граница выполняется, результат отрицательный** — тест на то, что реализация не «чинит» это молча |
| Одна стратегия недоступна 100% времени | её вес не влияет на результат; портфель эквивалентен пулу без неё |

**Проверка границы регрета — главный тест корректности.** Реализация Hedge, нарушающая собственную теоретическую границу на синтетике, содержит баг. Тест обязан уметь его поймать.

### 7.2 Корректность данных

- маска доступности: капитал недоступной стратегии идёт в кэш по ставке из конфига, а не теряется и не удваивается;
- нормировка весов: `Σ w_i = 1` на каждом шаге с точностью до эпсилон;
- отсутствие look-ahead: подмена всех данных после дня `t` на пропуски не меняет веса на день `t+1`. **Это автоматический тест, а не ручная проверка**;
- издержки переключения считаются один раз, не дважды (тест на кривой с известным оборотом);
- сходимость разложения: сумма вкладов по стратегиям равна общему P&L.

### 7.3 Воспроизводимость

Повторный прогон с тем же seed даёт побитово тот же результат. `RANDOM` использует seed только из конфига.

## 8. Чего не делать

| Не делать | Причина |
|---|---|
| Подбирать `η` по итоговому результату | подгонка. `η` берётся из теоретического `η* = √(8 ln N / T)`, остальное — только чувствительность |
| Добавлять признаки, режимы, фильтры в аллокатор | смысл блока E в том, что предсказание **не требуется**. Добавив предсказание, вы получите детектор, который уже провалился |
| Нормировать веса только по доступным стратегиям молча | это другая стратегия аллокации; она допустима как отдельный прогон, но не как деталь реализации |
| Исключать из пула убыточные стратегии | это look-ahead. Пул фиксируется до прогона и не пересматривается по результату |
| Строить дашборды и графики | нужны числа |
| Переходить к live-аллокации по положительному результату | результат на `in_sample` кривых — верхняя граница. Live требует отдельного решения |

| 5 | `HEDGE`, `EG`, `ONS`, `RANDOM` + тесты §7.1 | алгоритмы, прошедшие проверку границы регрета |
| 6 | Издержки переключения, `HEDGE_LAZY` | прогоны §5 |
| 7 | Отчёт | ответы на §6.3 |

**Этап 4 — настоящая точка остановки, а не формальность.** Он стоит несколько часов и может закрыть всю работу с положительным исходом для проекта: вопрос снят измерением, а не мнением.

## 10. Оговорки для README

- **Граница регрета относительна.** Она не обещает прибыли. Пул из убыточных стратегий даёт убыточный портфель при полном соблюдении гарантии.
- **Результат на `in_sample` кривых — верхняя граница.** Кривые получены с выбором параметров задним числом; аллокатор наследует это смещение.
- **Стенд не оправдывает ни одну стратегию пула.** Он отвечает только на вопрос о распределении между ними. Улучшение аллокации на закрытом пуле не делает пул рабочим.
- **Отрицательный результат — полноценный результат.** Он закрывает вопрос об аллокации, который сейчас держится на инструменте (детекторе), не прошедшем собственную проверку.
