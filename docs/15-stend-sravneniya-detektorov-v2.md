# Стенд сравнения детекторов режима — ТЗ на реализацию, v2

**Назначение:** документ написан как задание для исполнителя (Claude Code). Цель — не «сделать детектор», а **честно сравнить несколько алгоритмов на одной разметке и одних метриках и выбрать один**.

**Зависимости:** `01-detektor-rezhima-v2.md` (спецификация правилового кандидата), `04-validaciya-backtest.md` (протокол защиты от переобучения).
**Теоретическая база:** `Теория — база/t07` (метрики и их погрешность), `t08` (виды самообмана), `t09` (фильтрация и режимы).

**Что изменилось в v2:** добавлен кандидат volatility targeting (§5), журнал гипотез (§7), кросс-рыночная проверка (§8), режим доступа к отложенной выборке (§9), дефлированный Sharpe в метрики (§6.3). Полный список — в changelog.

**Главный принцип:** стенд ценен ровно настолько, насколько он способен забраковать нашу же любимую гипотезу. Если по итогам прогона победил тривиальный SMA200 — это валидный результат, а не повод «докрутить» композит.

## 2. Данные

- Инструмент: `BTC/USDT`, дневные свечи, с `2017-01-01` по текущую дату.
- Источник: `ccxt`, Binance основной, Kraken/Coinbase как резерв при расхождении.
- Формат: `DataFrame[open, high, low, close, volume]`, индекс — `DatetimeIndex`, UTC, без дыр.
- Кэш: parquet, перезагрузка только по явному флагу.

**Обязательные проверки при загрузке:**

- нет пропущенных дней (реиндексация по календарю, дыра → исключение, не `fillna`);
- нет дубликатов индекса;
- `high ≥ max(open, close)`, `low ≤ min(open, close)`;
- **запрещён `bfill` в любом виде.** Только `ffill`, и только с явным логом. Это не стилистика: `bfill` — буквальное протаскивание будущего в прошлое.

Ликвидации и on-chain на первом этапе **не подключаем**: истории мало, данные ревизуются (`t08`, раздел про ревизию), а сравнивать алгоритмы можно и на одной цене. Ось `S` из doc 01 v2 считается по волатильности и скорости просадки, `liq_pct` выключен.

## 3. Разметка истории (эталон для оценки)

Реализовать в `labeling/peak_trough.py`:

```
1. Найти кандидатов в локальные экстремумы (окно ±30 дней).
2. Чередование: пик → впадина → пик. Два подряд одного типа — оставить экстремальный.
3. Подъём от впадины к пику ≥ +50%  → отрезок BULL.
   Падение от пика к впадине ≥ −30% → отрезок BEAR.
   Отрезки, не проходящие порог, → RANGE.
4. Отрезки короче 30 дней поглощаются предыдущим.
```

Выход: `Series[state]` по всем датам, значения `{BULL, BEAR, RANGE}`.

**Разметка смотрит в будущее по построению.** Она допустима только в `eval/`. Импорт `labeling` в `detectors/` — ошибка сборки, покрывается тестом (§7).

Проверить глазами: разметка должна опознать топ декабря 2017, дно декабря 2018, дно марта 2020, топ ноября 2021, дно ноября 2022. Если не опознала — баг в дейтинге, а не «особенность рынка».

## 4. Единый интерфейс детектора

```python
class Detector(Protocol):
    name: str
    def fit(self, df: pd.DataFrame) -> None: ...
    def predict(self, df: pd.DataFrame) -> pd.Series: ...          # состояние на каждый день
    def predict_exposure(self, df: pd.DataFrame) -> pd.Series: ... # доля капитала в BTC, [0..1]
```

Контракт:

- `predict(df)[t]` зависит **только** от `df[:t]`. Главное требование, тестируется автоматически.
- `predict_exposure` по умолчанию реализован в базовом классе как отображение состояния через `ALLOCATION_MATRIX` (§6.2). Переопределяется только теми кандидатами, которые выдают непрерывную экспозицию напрямую — сейчас это `voltarget`.
- Для правиловых детекторов `fit` — no-op, но метод обязателен: протокол WFO применяется ко всем одинаково, иначе сравнение нечестное.
- Допустимые состояния: `{BULL, BEAR, RANGE, TRANSITION, CRASH}`. Детектор, у которого нет какого-то состояния, просто его не выдаёт.

## 5. Алгоритмы-кандидаты

| Ключ | Описание | Параметров |
|---|---|---|
| `baseline_always_range` | всегда RANGE, детектора нет | 0 |
| `baseline_sma200` | `close > SMA200 → BULL`, иначе `BEAR` | 0 |
| `baseline_voltarget` | **новое в v2**, см. ниже | 1 |
| `rules2d` | doc 01 v2, §2–3 | 4 |
| `cusum` | CUSUM по накопленному отклонению лог-доходности от нуля, два симметричных порога | 2 |
| `hmm` | `hmmlearn`, Gaussian, 3 состояния. Фичи: лог-доходность 1д, реализованная волатильность 14д | ~2 |
| `gmm` | `sklearn.GaussianMixture`, 4 кластера по [лог-доходность 20д, реал. вол. 14д, ER 90д, dist до SMA200] | ~1 |
| `ensemble` | голосование `rules2d` + `cusum` + `hmm`; разногласие → `TRANSITION` | 0 |

Отдельно: `buy_and_hold` — не детектор, а бенчмарк доходности, живёт в `eval/`.

### 5.1 baseline_voltarget — обязательный кандидат

Не классифицирует состояния вообще. Масштабирует экспозицию обратно пропорционально текущей волатильности:

```
exposure(t) = clip( σ_target / σ_реализ(t, окно 30д), 0, 1 )
```

`σ_target` — единственный параметр, задаётся как медиана реализованной волатильности BTC за период прогрева, не подбирается.

**Почему этот кандидат обязателен.** Из `t05`: предсказуемость волатильности на порядок выше предсказуемости направления. Из `t02`: реальный рост капитала равен `μ − σ²/2`, то есть стабилизация `σ` увеличивает рост напрямую. Volatility targeting использует самый прочный статистический факт и не использует самый слабый.

Есть заметный шанс, что он побьёт весь композит из трёх осей. Если так — это важный результат, а не досадное недоразумение.

### 5.2 Ловушки HMM и GMM

1. **Перестановка состояний.** Номер скрытого состояния не имеет смысла и меняется от прогона к прогону. Метки назначать по средней доходности внутри состояния **на обучающем окне**: наибольшая → BULL, наименьшая → BEAR, средняя → RANGE. Никогда по индексу.
2. **Переобучение на 3 циклах.** Ожидание, зафиксированное **до** эксперимента: HMM покажет хорошую in-sample картинку и посредственный out-of-sample. Это ожидаемый результат, его надо записать, а не «починить» подбором числа состояний.

## 6. Протокол оценки

### 6.1 Walk-forward

- Прогрев: первые 2 года (нужны SMA200 + ATR90 + ранги). Прогретые дни в оценку не входят и **не заполняются** ничем.
- Расширяющееся окно: обучение на `[start, T]`, предсказание на `(T, T+90 дней]`, шаг 90 дней.
- Параметры из `configs/params.yaml` фиксируются один раз и в цикле WFO не меняются.

**Важно (`t08`):** walk-forward не делает честными параметры, выбранные по всей истории. Протокол проверяет процедуру, а не число.

### 6.2 Экономический прокси

Грубая модель аллокации, достаточная для сравнения детекторов между собой:

| Состояние | Экспозиция в BTC |
|---|---|
| BULL | 100% |
| TRANSITION | 50% |
| RANGE | 0% (кэш под 8% годовых — прокси нейтрального ядра S1) |
| BEAR | 0% |
| CRASH | 0% |

- Реаллокация: равными шагами за 5 торговых дней. Вход в `CRASH` — мгновенно.
- Комиссия: 0.05% от оборота при каждом изменении экспозиции.
- Проскальзывание: 0.05% дополнительно.
- Для `voltarget` экспозиция берётся напрямую из `predict_exposure`, реаллокация та же.

В отчёте пометить: **это прокси, а не P&L бота.** Абсолютные числа отсюда никуда не переносятся, сравнимы только относительные.

### 6.3 Метрики

Технические: `lag_days` (медиана), `flips_per_year`, `state_accuracy`, `false_bear_rate`, `turnover`.

Экономические: `MaxDD`, `CAGR`, `Sharpe`, и главное — **Δ MaxDD / Δ CAGR относительно buy & hold**.

**Обязательно к каждому Sharpe (новое в v2):**

- доверительный интервал по формуле `SE(S) ≈ √((1 + S²/2)/T)`, где `T` — годы;
- **дефлированный Sharpe** `S_defl ≈ S − SE(S)·√(2 ln N)`, где `N` — число гипотез из журнала (§7).

Голый Sharpe без интервала в отчёт не попадает. Причина в `t07`: при 3 годах данных интервал вокруг `S = 1.0` шире, чем расстояние от нуля до двойки.

### 6.4 Критерий выбора

Победитель — по `Δ MaxDD / Δ CAGR` на out-of-sample.

**Правило отсечения сложности:** кандидат, не превзошедший `baseline_sma200` **и** `baseline_voltarget`, отвергается независимо от того, сколько сил в него вложено. Если побеждает baseline — это и есть результат работы, и детектор в проде должен стать однострочником.

## 7. Журнал гипотез (новое в v2)

Файл `reports/hypotheses.md`, **append-only**: строки не редактируются и не удаляются.

Каждая проверенная идея — одна запись:

```
| дата | гипотеза | мотивация | результат | решение |
```

Записывается **всё**, включая:

- идеи, отброшенные после первого взгляда на результат;
- варианты параметров, прогнанные «просто посмотреть»;
- отладочные прогоны, которые случайно показали интересный результат.

**Зачем.** Из `t08`: ожидаемый Sharpe лучшей из `N` бесполезных стратегий равен `σ_S·√(2 ln N)`. При 3 годах данных и 50 проверенных гипотезах это ≈ 1.96. То есть результат, выглядящий как открытие, ровно соответствует чистому перебору.

Без журнала `N` неизвестно, и оценить значимость находки невозможно. Перебор редко бывает формальным — он накапливается незаметно из отдельных «а давай попробуем», и счётчик надо вести принудительно.

Итоговое `N` из журнала подставляется в дефлированный Sharpe (§6.3).

## 8. Кросс-рыночная проверка (новое в v2)

Выполняется **после** выбора победителя, до любых выводов о его пригодности.

Победивший детектор без единого изменения параметров прогоняется на:

| Рынок | Инструмент | Период |
|---|---|---|
| Крипто | ETH | 2017– |
| Акции | S&P 500 (SPY) | 1993– |
| Золото | XAU/USD | 1990– |
| Нефть | WTI | 1990– |
| Валюта | EUR/USD | 1999– |

Данные: `yfinance` или аналог, дневные закрытия достаточно.

**Критерий:** эффект должен сохраняться по знаку и порядку величины. Не «те же цифры» — рынки разные, — а «просадка снижается, доходность частично теряется, отношение остаётся в разумных пределах».

**Интерпретация результата:**

- Работает везде → сильное свидетельство робастности. Ценнее любого улучшения метрик на BTC.
- Работает только на BTC и только на нашем окне → почти наверняка подгонка, каким бы красивым ни был основной результат.
- Работает на большинстве, ломается на одном → разобраться, чем этот рынок отличается; часто это содержательное открытие.

**Почему это самая ценная проверка.** Наша беда — короткая история (`t05`: точность оценки средней доходности BTC ±25 п.п.). Другие рынки дают десятилетия данных бесплатно, тем же кодом. Информации отсюда больше, чем от любой возни с параметрами.

## 9. Режим доступа к отложенной выборке (новое в v2)

**Отложенная выборка:** последние 18 месяцев данных. Резервируются до начала работы.

**Правила:**

1. В разработке, отладке и анализе устойчивости эти данные **не используются вообще**. Все прогоны — на истории до границы.
2. Обращение к отложенной выборке допускается **не более двух раз** за весь проект.
3. Каждое обращение фиксируется в журнале гипотез с датой и причиной.
4. После обращения изменение модели требует новой отложенной выборки, которой у нас нет.

**Зачем.** Из `t08`: при итеративной доработке «по результату на тесте» тестовая выборка перестаёт быть тестовой к десятой итерации. Формально протокол соблюдён, фактически информация просочилась в модель через принимаемые решения. Ограничение числа обращений — единственная работающая защита.

## 10. Антибаг-чеклист

Каждый пункт — автотест или явная запись в отчёте.

1. **Causality test (критично).** Для 20 случайных дат `t`: `predict(df[:t]).iloc[-1]` совпадает с `predict(df).loc[t]`. Обязателен для **каждого** детектора, включая baseline.
2. **Изоляция разметки.** Ни один модуль в `detectors/` не импортирует `labeling`. Проверять AST-обходом, не grep'ом.
3. **Тест на перемешанных данных.** Прогнать все детекторы на ряду со случайно перемешанными дневными доходностями. Экономическое преимущество над buy & hold должно исчезнуть. 20 перемешиваний, в отчёт — распределение.
4. **Warm-up не заполняется.** Первые `max(200, 90) + запас` дней отбрасываются, без `ffill`-хвостов.
5. **Корреляции.** `corr(D, T)`, `corr(D, S)`, `corr(T, S)` на всей истории. Если `|corr| > 0.8` — оси не ортогональны, конструкция v2 не работает, написать прямо.
6. **Частота CRASH.** Целевое 2–5 в год. Если 0 или 20 — зафиксировать и **не подкручивать**, вынести в открытые вопросы.
7. **Sanity-check baseline.** `baseline_sma200` на BTC 2017–2025 снижает MaxDD примерно с −80% до −50…−65% и заметно проигрывает buy & hold по CAGR. Если он лучше по обоим — утечка или забытые комиссии.
8. **Стабильность HMM.** 5 разных `random_state`. Границы режимов гуляют больше чем на 2 недели → модель нестабильна, отметить.
9. **Комиссии применяются.** Прогон с 0% и 1% даёт разный результат.
10. **Детерминированность.** Два прогона с одним конфигом — идентичный отчёт.
11. **Журнал гипотез непуст и согласован** с числом прогонов в отчётах (новое в v2).
12. **Кросс-рыночный прогон выполнен** для победителя (новое в v2).

## 11. Чего делать не надо

- **Не подбирать пороги.** Ни grid search, ни «попробуем 0.35 вместо 0.40». Коммит с `params.yaml` — до коммита с результатами.
- **Не добавлять фичи после первого прогона.** Это уже вторая итерация, с отдельной отложенной выборкой, которой нет.
- **Не исключать «аномальные» периоды.** Март 2020 и май 2021 — не выбросы, это ровно те дни, ради которых детектор существует.
- **Не улучшать разметку под результат.**
- **Не редактировать журнал гипотез задним числом** (новое в v2). Запись о неудачной идее — это данные, а не мусор.
