# 217. Динамический отступ: проверить на истории, а не на вере

27.10.2026. По вопросу владельца к 216: на что настроена модель, зависит ли она от включённых функций, и можно ли считать отступ на скользящем окне — в том числе «большое окно как основа плюс часовое для всплесков» — и проверить в симуляции, больше ли так заработаем.

## Кратко

1. **Модель — не подогнанная формула, а прогон.** Она берёт записанные сделки и книгу Revolut за период и прогоняет через них логику бота с его настройками. Подстроечных чисел два на монету — доля исполнения по сторонам (216 §9).
2. **От включённых функций зависит.** Оптимум считается для конкретного набора: уровни, скос, потолок, лимит постановок, очередь, ранний аск, «дальняя». Меняется набор — модель надо перегнать. Функции, которых в модели нет — затык, календарь, парковка в бурю, порядок замен, — она не учитывает.
3. **Скользящее окно — правильная идея, но её саму надо проверить.** Правило «отступ по прошлой неделе» может зарабатывать больше постоянного, а может гоняться за шумом. Проверка — «шаг вперёд» на истории (§1).
4. **Часовое окно отступ не посчитает.** До отступа 12 б.п. на BTC доходит меньше одной сделки в час на сторону (216 §2), по одному часу оптимум не найти. Часовое окно годится только чтобы **узнать состояние часа** (тихо, обычно, оживлённо) и **выбрать отступ из таблицы**, которую заранее посчитали на большом окне для каждого состояния (§2).
5. **Оценивать должен стенд, а не та же модель.** Иначе модель сама себе ставит оценку.

---

## 1. Проверка А — недельное окно, шаг вперёд

**Как:**
- для каждой недели k берём **только прошлые** данные — 1 или 2 недели до k;
- модель (`FlowSim2`, как в мониторе) выбирает отступ каждому боту по правилу монитора: менять, только если оптимум вышел за плато;
- **стенд** прогоняет неделю k с этим отступом;
- сравнение — с тем же стендом на постоянном живом отступе на той же неделе.

**Окна:** w1–w6, плюс новые недели по мере накопления.

Недель мало, поэтому дополнительно — суточный шаг: окно 7 суток, сдвиг на сутки, оценка на следующих сутках. Так точек для сравнения больше.

**Мерка** — деньги с переоценкой и раскладка на торговлю и запас (216 §1).

**Решение, записано до расчёта.** Динамика лучше постоянного отступа, если одновременно:
- в сумме за все недели больше хотя бы на 5%;
- больше в большинстве недель (или суток);
- выигрыш идёт из торговой части, а не из запаса.

Иначе остаётся постоянный отступ с монитором «два отчёта подряд» (216 §8).

## 2. Проверка Б — большое окно плюс состояние часа

**Как:**
1. На большом окне (2–4 недели, только прошлое) модель считает оптимум отдельно для каждого **состояния часа**. Состояния — только то, что не зависит от направления цены:
   - поток: сколько сделок дошло до +10 б.п. за прошлый час — тихо / обычно / оживлённо (как в «Отступ, скос и запас» §4.3, там тишина держится часами);
   - размах цены Бинанса за прошлый час — спокойно / бурно.

   Получается таблица «состояние → отступ» для каждого бота.
2. Каждый час бот определяет состояние по прошлому часу и берёт отступ из таблицы.
3. Стенд прогоняет следующую неделю с таким расписанием отступов. Сравнение — с постоянным отступом и с проверкой А.

**Нужно в стенде:** отступ по расписанию — файл «время → отступ по боту». Замена заявки постановок не тратит, поэтому частая смена отступа бюджет почти не трогает.

**Решение** — то же, что в §1. Плюс таблица должна быть устойчивой: оптимум для одного и того же состояния на соседних окнах не должен прыгать больше ширины плато.

⚠️ **Чего ждать.** Раньше по классам волатильности оптимум не двигался (A74, 168), а таблица оптимумов по состояниям выходила шумной. Тогда в состояния входило направление часа, а оценка была грубее. Теперь модель быстрая и откалибрована, поэтому проверить дёшево. Но заметного выигрыша заранее не обещаю.
