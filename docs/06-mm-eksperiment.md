# Экспериментальный маркет-мейкинг на малоликвидной бирже

Дополнение к пакету документов 00–05. Статус: **исследовательская ветка**, не боевая стратегия. Цель — не доход, а обучение: собрать работающий MM-стек (референсная цена, управление котировками и инвентарём, детект токсичного потока) в среде, где цена ошибки минимальна. Лимит капитала: ≤ 2% общего, и только суммы, полную потерю которых проект переживает спокойно (риск площадки — максимальный из всех наших веток).

---

## 1. Что мы проверяем (гипотезы эксперимента)

| # | Гипотеза | Как проверяем |
|---|----------|---------------|
| H1 | На площадке есть живой (не wash) поток ретейла | Фаза 0: пассивное наблюдение + мелкие котировки |
| H2 | Спред пары покрывает потери от токсичного потока | Метрика adverse selection (§6) за ≥ 2 недели котирования |
| H3 | Референсное котирование + быстрое снятие ордеров достаточно защищают от арбитражных снайперов | Доля исполнений в моменты движения референса |
| H4 | Инвентарь управляем: перекос позиции возвращается к нулю без принудительных сливов | Распределение инвентаря по времени |
| H5 | Итоговая экономика > 0 после всех потерь | Полный P&L-разрез (§6) |

Провал любой из H1–H3 — валидный результат эксперимента: мы узнали это на копейки.

---

## 2. Выбор площадки и пары (фаза −1)

Чек-лист площадки:
- Мейкер-комиссия 0 или отрицательная; тейкер — неважен (мы не тейкаем, кроме аварий).
- Работающий WebSocket на стакан и сделки + REST на ордера; вменяемые рейт-лимиты (нам нужны частые cancel/replace).
- API-ключи без права вывода; вывод — только вручную с 2FA.
- История выводов средств: поиск жалоб за последние 6–12 мес. Любые системные задержки выводов → площадка отклоняется.
- Тестовая проверка: завести минимум, поторговать, вывести. Полный круг ДО основного капитала.

Чек-лист пары:
- Актив-«спутник» существует на ликвидной бирже (нужен референс цены!). Экзотика, торгующаяся только здесь, не подходит — нечем котировать и некуда бежать.
- Спред устойчиво ≥ 0.3% (иначе экономики нет даже в теории).
- Видимый суточный объём $20k–500k (меньше — мертво, больше — там уже кто-то профессионально стоит).
- В стакане нет признаков действующего ММ: плотные симметричные котировки, мгновенно переставляющиеся за референсом. Есть → искать другую пару, конкурировать не с чем.

## 3. Фаза 0: наблюдение без торговли (1–2 недели)

Пишется только сборщик данных, ни одного ордера:
- Полный лог стакана (снапшоты + дельты) и ленты сделок пары.
- Параллельно — лента той же пары с референсной биржи.

Анализ фазы 0:
- **Оценка wash trading:** доля сделок, исполняющихся внутри спреда без изменения стакана, серии одинаковых объёмов, круглосуточная равномерность (живой ретейл имеет суточный профиль). Грубая эвристика: если > 60% объёма выглядит синтетикой — H1 отклонена, площадка меняется.
- **Профиль спреда:** распределение по времени суток; когда он шире — там наш доход.
- **Лаг цены:** насколько локальная цена отстаёт от референса при движениях (это будущее окно уязвимости для снайперов, H3).
- Симуляция «если бы мы стояли в стакане»: по логам оценить, как часто нас бы исполняли и в какие моменты (грубая, но бесплатная прикидка H2).

## 4. Архитектура бота

Пять компонентов, разделённых по процессам (падение одного не убивает контроль рисков):

```
┌────────────────────────────────────────────────────────┐
│ 1. Reference Feed                                      │
│ WebSocket ликвидной биржи → mid-price, волатильность   │
│ EMA, «флаг быстрого движения» (|Δ| > k·σ за T сек)     │
└──────────────┬─────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────┐
│ 2. Quote Engine (ядро)                                 │
│ считает целевые bid/ask из референса + инвентаря       │
└──────────────┬─────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────┐
│ 3. Order Manager                                       │
│ cancel/replace до целевых котировок, учёт рейт-лимитов,│
│ сверка своего состояния с биржей                       │
└──────────────┬─────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────┐
│ 4. Inventory & Risk Monitor (отдельный процесс)        │
│ позиция, лимиты, kill-switch                           │
└──────────────┬─────────────────────────────────────────┘
┌──────────────▼─────────────────────────────────────────┐
│ 5. Recorder                                            │
│ каждое исполнение + снимок референса в момент          │
│ исполнения → база (без этого анализ §6 невозможен)     │
└────────────────────────────────────────────────────────┘
```

### Логика Quote Engine (стартовая версия)

```
mid_ref   = mid-price референсной биржи
skew      = -c · (inventory / max_inventory)        # перекос против инвентаря
half_spr  = max(min_half_spread, α · σ_ref)         # шире при волатильности

bid = mid_ref · (1 + skew - half_spr)
ask = mid_ref · (1 + skew + half_spr)
```

Стартовые параметры: `min_half_spread` = 0.25% (уже фактического полуспреда пары — иначе нас никогда не исполнят, шире смысла нет), `c` = 0.5–1.0, `α` подобрать так, чтобы при спокойном референсе котировки были чуть внутри текущего спреда площадки.

Смысл `skew`: купили — котировки смещаются вниз, чтобы охотнее продавать и неохотнее докупать. Это главный и почти единственный механизм управления инвентарём; принудительные сливы маркетом — аварийный случай.

### Правила защиты (важнее логики котирования)

1. **Fast-move pull:** флаг быстрого движения референса → немедленный cancel ВСЕХ котировок, возврат через N секунд после стабилизации. Это основная защита H3; латентность этого пути — единственное место, где скорость имеет значение.
2. **Stale-data stop:** референсный фид молчит > 3 сек → снять котировки. Котировать вслепую запрещено.
3. **Инвентарные лимиты:** |inventory| > 70% max → котируется только разгружающая сторона; > 100% → разгрузка тейкером на референсной бирже (если актив там есть) или локально мелкими порциями; событие в журнал как инцидент.
4. **Дневной стоп:** убыток дня > X (задать в абсолюте, например 2% капитала ветки) → полная остановка до ручного разбора.
5. **Sanity-check цены:** собственная котировка отклонилась от референса > 3% (баг!) → kill-switch.
6. **Сверка состояния:** раз в минуту — открытые ордера и позиция по REST против внутреннего учёта; расхождение → стоп новых ордеров.

### Стек

Python достаточно (наши скорости — сотни миллисекунд, не микросекунды): `asyncio` + `websockets`/ccxt.pro, состояние в памяти, Recorder пишет в SQLite/Postgres. Один VPS недалеко от серверов референсной биржи уменьшит латентность fast-move pull — единственная «инфраструктурная» инвестиция, которая тут оправдана.

## 5. Фазы эксперимента

| Фаза | Содержание | Длительность | Критерий перехода |
|------|-----------|--------------|-------------------|
| −1 | Выбор площадки/пары, тестовый круг ввод-вывод | — | Чек-листы §2 |
| 0 | Наблюдение, сбор данных, оценка wash | 1–2 нед. | H1 не отклонена |
| 1 | Микро-котирование: минимальные размеры, широкий спред (0.4–0.5% half) | 2 нед. | Бот стабилен, Recorder полон, нет инцидентов учёта |
| 2 | Рабочий спред, включён skew, fast-move pull боевой | 4 нед. | Метрики §6 считаются ежедневно |
| 3 | Итоговый анализ, вердикт по H1–H5 | 1 нед. | Отчёт: закрыть / продолжить / перенести стек на другую пару |

Правило одного изменения между фазами — как в док. 04 §6.

## 6. Что анализировать (ядро документа)

### Разрез P&L — три компоненты, считать раздельно

```
P&L = spread_pnl + inventory_pnl + fees(≈0)

spread_pnl    = Σ по round-trip'ам: (цена продажи − цена покупки) · объём
inventory_pnl = переоценка незакрытого инвентаря по референсу
```

Здоровый ММ: spread_pnl стабильно > 0, inventory_pnl шумит вокруг нуля. Если прибыль приходит из inventory_pnl — мы не мейкер, а случайный направленный трейдер, и результат — удача.

### Adverse selection / токсичность (проверка H2–H3, главная метрика)

Для каждого исполнения Recorder сохранил референсный mid в момент сделки. Считаем **markout**: изменение референсного mid через 10 сек / 1 мин / 10 мин после исполнения, в сторону нашей сделки.

```
markout_T = side · (mid_ref(t+T) − mid_ref(t)) / mid_ref(t),  side: buy=+1, sell=−1
```

- Средний markout сильно отрицательный (нас исполняют перед движением против нас) → поток токсичен. Смотрим распределение: если токсичность сконцентрирована в моменты движения референса → H3, ужесточать fast-move pull; если размазана → на паре сидит информированный поток, пара не годится.
- Практический порог: |средний markout_1min| должен быть заметно меньше половины нашего спреда. Иначе экономика мертва: `edge_на_сделку ≈ half_spread + средний markout` — это число обязано быть положительным с запасом.

### Инвентарь (H4)

- Распределение инвентаря по времени: медиана около нуля, хвосты внутри лимитов.
- Время полувозврата перекоса к нулю: растёт от недели к неделе → skew слаб или поток односторонний.
- Доля времени в состоянии «котируется одна сторона» — это упущенный доход, если > 20% времени — пересмотр `c` или max_inventory.

### Качество исполнения и участие

- Fill rate: сколько наших котировок доживает до исполнения vs снимается. Исполнений почти нет → мы слишком широки или объём фейковый (возврат к H1).
- Наша доля в реальном объёме пары: приближается к 40–50% → потолок достигнут, масштабирование бессмысленно.
- Uptime котирования: доля времени с двусторонними котировками в рынке.

### Операционные метрики

- Латентность цикла «референс дёрнулся → наши ордера сняты» (перцентили; p99 — то, что нас убивает).
- Частота cancel/replace против рейт-лимитов площадки.
- Число расхождений сверки состояния (цель — ноль).

### Итоговый вердикт фазы 3

Отчёт по шаблону: H1–H5 с числами; годовая экстраполяция spread_pnl честно против риска площадки (заработать 15% годовых на капитале, который с вероятностью в проценты исчезнет целиком, — плохая сделка, и это надо записать явно); чему научился стек и что из него переносимо (Reference Feed, markout-анализ и inventory-логика переносимы на любую площадку — это и есть главный актив эксперимента).

## 7. Связь с основным пакетом

- Капитал ветки — из «свободного резерва» матрицы аллокации (док. 00 §4), ≤ 2%.
- Риск площадки: на эту биржу НЕ распространяется лимит 50% (док. 03 §1) — здесь лимит 2% и точка; средства сверх рабочего минимума выводятся еженедельно.
- Recorder и markout-анализ — прямое переиспользование для оценки качества исполнения основных стратегий (сверка факт vs модель издержек, док. 03 §8).
- Ветка запускается строго после этапа 3 дорожной карты (живой S1): эксперимент не должен конкурировать за внимание с ядром.
