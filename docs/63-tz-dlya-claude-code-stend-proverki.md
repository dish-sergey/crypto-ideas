# ТЗ для Claude Code: стенд проверки маркет-мейкинга на Revolut X

**Что строим.** Приложение из трёх модулей: сборщик публичных данных, симулятор исполнения на собранных данных, отчёт с конкретными числами. Цель — закрыть открытые вопросы **до** того, как на биржу попадёт хоть один реальный ордер.

**Что НЕ строим на этом этапе.** Торгового бота. Приложение не отправляет ордера и не хранит торговые ключи. Режим реальной торговли добавляется отдельным этапом только после положительного отчёта.

---

## 0. Главное предупреждение исполнителю

**Симуляция маркет-мейкинга почти всегда получается слишком оптимистичной, и всегда по одной причине: неверная модель исполнения.**

Наивное допущение «цена коснулась моей лимитки → меня исполнили» завышает результат в разы. В реальности:

- при касании цены исполняется очередь перед вами, а не вы;
- вас исполняют преимущественно тогда, когда это невыгодно (неблагоприятный отбор);
- при движении вниз исполняется только бид, аск не исполняется никогда, и вы набираете инвентарь.

**Если по итогам работы симулятор покажет красивую эквити — первая гипотеза должна быть «ошибка в модели исполнения», а не «стратегия работает».** В §5.6 перечислены запрещённые допущения; их нарушение — дефект, а не оптимизация.

## 2. Стек и общие требования

- **Python 3.11+**, `httpx` (async), `pandas`, `pyarrow`, `pydantic`, `pytest`. Без тяжёлых фреймворков.
- Хранилище: **SQLite** для метаданных прогонов + **parquet** для рядов. Никакого внешнего сервера.
- Конфигурация — один `config.yaml`, все параметры стратегии и издержек **только оттуда**, никаких констант в коде.
- Всё время — **UTC, в миллисекундах, целыми числами**. Ни одной naive-datetime в коде.
- Логирование структурное (JSON-строки), уровень настраивается.
- `README.md` с командами запуска каждого модуля.

**Отдельное требование к воспроизводимости.** Каждый прогон симулятора пишет в SQLite запись: git-хэш, полный конфиг, диапазон данных, версия модели исполнения, результат. Без этой записи прогон недействителен.

## 3. Модуль 1: коллектор

### 3.1 Endpoint

Базовый URL: `https://revx.revolut.com`

| Назначение | Метод и путь | Параметры |
|---|---|---|
| Список пар | `GET /api/1.0/public/configuration/pairs` | `region=EEA` |
| Книга заявок | `GET /api/2.0/public/order-book/{SYMBOL}` | `limit`, `region=EEA` |
| Лента сделок | `GET /api/1.0/public/trades/all` | `symbol`, `start_date`, `end_date`, `cursor`, `limit` |

Формат символа в пути книги — через дефис: `BTC-USDC`, `ETH-USD`.

Авторизация не требуется. Ключи API на этом этапе не нужны вообще.

### 3.2 Известные подводные камни — обработать явно

**Порядок сортировки в ответе книги не гарантирован.** В наблюдённом ответе массив `asks` шёл в **убывающем** порядке, то есть первый элемент не является лучшим аском. Наивное чтение `asks[0]` даёт спред в несколько раз больше реального.

Требование: **после парсинга явно сортировать** — биды по убыванию цены, аски по возрастанию — и **проверять инвариант** `best_ask > best_bid`. При нарушении — писать запись в журнал аномалий и пропускать снимок, а не падать и не молча чинить.

**429 Too Many Requests наблюдался** при опросе `/order-book/BTC-USD`. Требуется:

- глобальный лимитер запросов с настраиваемым потолком (в запросах/секунду);
- экспоненциальный backoff с джиттером при 429/5xx;
- счётчик 429 в метриках прогона: если доля 429 выше 1%, отчёт помечается как неполный;
- определить фактический лимит **эмпирически**: отдельный скрипт медленно повышает частоту до первого устойчивого 429 и записывает найденный потолок в `config.yaml`.

**`limit=100` на ленте сделок упирается в потолок.** Обязательна пагинация по `cursor` до исчерпания диапазона. Если пагинация не реализована, поток будет систематически занижен.

### 3.3 Одновременность — критическое требование

Сравнение середины USDC-книги с USD-книгой имеет смысл **только если снимки взяты одновременно**. Разнесённые во времени снимки дают дрейф цены, неотличимый от базиса.

Требование:

- пара `{ASSET}/USDC` и `{ASSET}/USD` запрашиваются **параллельно, в одном asyncio-батче**;
- в снимок пишутся **оба** времени: `t_request_sent` и `t_response_received` для каждой ноги;
- вычисляется `skew_ms` = разница между временами получения двух ног;
- **снимки с `skew_ms` больше порога (по умолчанию 250 мс) исключаются** из расчёта базиса, но сохраняются в сыром виде с флагом.

Доля исключённых снимков — обязательное поле отчёта.

### 3.4 Что собирать

**Вселенная:** 20 USDC-пар и их USD-аналоги (40 символов). Список USDC-пар берётся из endpoint пар динамически, не хардкодится.

| Поток | Частота | Содержание |
|---|---|---|
| Книга | каждые 5 с (настраивается) | 5 уровней с обеих сторон, обе ноги пары, оба времени, `skew_ms` |
| Сделки | непрерывно, с пагинацией | время, цена, размер, сторона если отдаётся API |
| Конфигурация пар | раз в сутки | отслеживать появление и исчезновение пар |

**Минимальная длительность сбора до первого отчёта — 7 суток непрерывно.** Обязательно включить выходные: гипотеза о розничном потоке предполагает разное поведение в будни и выходные, и это надо увидеть.

### 3.5 Устойчивость

Коллектор — долгоживущий процесс. Требуется: переживание разрывов сети без потери уже записанного, докачка пропущенного окна сделок после простоя, идемпотентная запись (повторный запуск не дублирует), healthcheck-файл с временем последней успешной записи.

**Данные книги невосполнимы задним числом.** Приоритет надёжности выше приоритета функциональности: лучше собрать меньше полей, но без пропусков.

## 4. Модуль 2: симулятор

Симулятор проигрывает собранные данные и моделирует поведение маркет-мейкера. Это ядро задания.

### 4.1 Справедливая цена

**Опорная цена берётся из USD-книги**, а не из USDC-книги, в которой торгуем.

```
fair_usdc(asset, t) = mid_usd(asset, t) / rate_usdc_usd(t)
```

**Курс `rate_usdc_usd` вычисляется по многим парам, а не по одной.** Для каждого актива `i` в наборе ликвидных неммемкоин-пар:

```
implied_i(t) = mid_usd(i, t) / mid_usdc(i, t)
rate_usdc_usd(t) = median_i( implied_i(t) )
```

Медиана, а не среднее — устойчивость к одной разъехавшейся книге. Мемкоины (DOGE, SHIB, PEPE, BONK, TRUMP) в расчёт курса **не входят**, но котироваться могут.

Остаток `implied_i(t) − rate_usdc_usd(t)` — это локальное отклонение конкретной пары. Симулятор должен уметь использовать его как опциональный сигнал скоса и уметь **не** использовать (флаг в конфиге), чтобы измерить вклад отдельно.

**Обязательная проверка:** если разброс `implied_i` по парам превышает порог, курс считается ненадёжным, и котирование в этот момент приостанавливается. Доля такого времени — поле отчёта.

### 4.2 Логика котирования

Параметры из конфига: отступ `d` от справедливой цены, номинал заявки, потолок инвентаря, коэффициент скоса, порог перевыставления.

```
skew        = inventory / inventory_cap          # от -1 до +1
bid_price   = fair * (1 - d - skew_k * skew)
ask_price   = fair * (1 + d - skew_k * skew)
```

Скос двигает **обе** котировки в одну сторону: при полном инвентаре бид уходит вниз и перестаёт исполняться, аск придвигается к справедливой цене и разгружает позицию.

**Жёсткие правила:**

- при `inventory >= inventory_cap` бид не выставляется вообще;
- при `inventory <= 0` аск не выставляется (спот, шортить нечем — это не опция, а физика);
- все заявки строго `post-only`;
- перевыставление только при отклонении цены больше порога — иначе счётчик перевыставлений уйдёт в тысячи и упрётся в rate limit.

Симулятор считает **число перевыставлений в сутки** и сверяет с найденным лимитом запросов. Стратегия, требующая больше запросов, чем разрешено — нереализуема, и это отдельный вердикт отчёта.

### 4.3 Модель исполнения — самая важная часть

**Заявка исполняется только тогда, когда через её цену прошёл достаточный объём сделок, чтобы выбрать очередь перед ней.**

Алгоритм:

1. При постановке заявки на цену `P` определить `queue_ahead`:
   - если на уровне `P` в последнем снимке есть объём — `queue_ahead = ` этот объём (мы встаём в конец);
   - если мы **улучшаем** книгу и создаём новый уровень — `queue_ahead = 0`;
   - если уровень `P` вне видимых 5 уровней — **заявка считается неисполнимой**, пока не попадёт в видимую часть.
2. Для каждой сделки из ленты определить сторону агрессора и цену.
3. Если сделка агрессивна против нашей стороны и её цена достигает `P` или проходит глубже — уменьшить `queue_ahead` на объём сделки.
4. Как только `queue_ahead <= 0`, остаток объёма сделки исполняет нашу заявку — частично или полностью.
5. Частичные исполнения обязательны к поддержке. Округление размеров — по `base_step` и `quote_step` из конфигурации пары.

**Определение стороны агрессора.** Если API не отдаёт сторону, выводить по правилу: цена сделки ближе к аску последнего снимка → покупатель-агрессор, ближе к биду → продавец-агрессор. При равенстве — помечать как неопределённую и в расчёт исполнений **не** брать. Доля неопределённых сделок — поле отчёта; если она выше 20%, модель исполнения признаётся ненадёжной.

**Консервативность при неопределённости.** Данные дискретны — снимки раз в 5 секунд, книга всего 5 уровней. Везде, где модель может трактовать ситуацию в свою пользу или против, **выбирается вариант против нас**. Конкретно: очередь перед нами не уменьшается от отмен чужих заявок (мы их не видим); при неоднозначности стороны агрессора исполнения не происходит; при одновременном срабатывании бида и аска в одном 5-секундном окне исполняется только невыгодная нам сторона.

### 4.4 Учёт P&L — с разложением

Итоговый P&L раскладывается на компоненты, и разложение обязано сходиться с общим результатом:

```
total = spread_capture + inventory_pnl - fees
```

| Компонента | Определение |
|---|---|
| `spread_capture` | сумма по исполнениям: `(fair_at_fill - fill_price) * size * side` |
| `inventory_pnl` | переоценка удерживаемого инвентаря по справедливой цене |
| `fees` | комиссия по фактическому типу исполнения |

**Это разложение — главный результат стенда.** Оно отвечает на вопрос, который иначе останется закрытым: заработала стратегия на спреде или на том, что рынок случайно вырос, пока она держала лонг.

Инвентарь оценивается **по справедливой цене из USD-книги**, а не по последней сделке в USDC-книге. Оценка по редкой сделке в тонкой книге даёт шум, который легко принять за результат.

### 4.5 Неблагоприятный отбор — решающее измерение

Для каждого исполнения считать markout по опорной цене:

```
markout(Δ) = (fair(t_fill + Δ) - fill_price) * side
```

для Δ ∈ {0, 10 с, 60 с, 300 с}.

Отчёт даёт распределение (среднее, медиана, квартили) по каждому Δ, отдельно по покупкам и продажам, отдельно по парам.

**Интерпретация, которую надо заложить в отчёт явно:**

| Наблюдение | Вывод |
|---|---|
| `markout(0) > 0`, `markout(60с) ≈ markout(0)` | вас исполняет неинформированный поток. Гипотеза подтверждается |
| `markout(0) > 0`, но `markout(60с)` заметно ниже | классический неблагоприятный отбор: спред реален, но забирает его не тот, кто котирует |
| `markout(60с) < 0` | **стратегия мертва**, независимо от того, что показывает эквити |

Это и есть тот самый вопрос, который нельзя решить снимками книги.

### 4.6 Запрещённые допущения

Нарушение любого пункта — дефект реализации:

1. Исполнение по факту касания цены без учёта очереди.
2. Исполнение всего объёма заявки одной сделкой без проверки размера.
3. Использование `mid` USDC-книги как справедливой цены.
4. Использование будущих данных для решения в момент `t` — включая снимок, полученный **после** `t`.
5. Курс USDC/USD, принятый равным 1.0000.
6. Игнорирование `base_step` и `quote_step` при округлении.
7. Предположение, что заявка вне видимых 5 уровней может исполниться.
8. Уменьшение очереди перед нами от неподтверждённых событий.
9. Мгновенное перевыставление без учёта лимита запросов.
10. Оценка инвентаря по последней сделке в тонкой книге.

### 4.7 Обязательные прогоны

| Прогон | Назначение |
|---|---|
| **Базовый** | maker 0%, отступ `d` из конфига |
| **Чувствительность к комиссии** | maker ∈ {0%, 0.01%, 0.02%, 0.05%} — при какой комиссии стратегия умирает |
| **Чувствительность к отступу** | `d` ∈ {0.02%, 0.04%, 0.06%, 0.10%} |
| **Чувствительность к потолку инвентаря** | 3 значения |
| **Контроль: buy & hold** | держать средний инвентарь стратегии тот же период, без торговли |
| **Контроль: случайные котировки** | тот же темп исполнений, но цены выставляются случайно вокруг справедливой |
| **Издержки ×1.5** | пессимистичный прогон |
| **По времени суток и дню недели** | будни против выходных, рабочие часы против ночи |

**Два контроля обязательны и являются главными.** Buy & hold отвечает, не был ли весь результат направленным движением. Случайные котировки отвечают, есть ли ценность в **выборе цен** или работает только сам факт присутствия в книге. Стратегия, не превосходящая оба контроля, отклоняется.

## 5. Модуль 3: отчёт

Один markdown-файл плюс parquet с сырыми результатами. Никаких дашбордов на этом этапе.

### 5.1 Раздел «Данные»

Период, аптайм коллектора, доля 429, доля снимков, отброшенных по `skew_ms`, доля сделок с неопределённым агрессором, доля времени с ненадёжным курсом USDC/USD, число пропущенных окон.

**Если аптайм ниже 95% или доля отброшенных снимков выше 10% — отчёт помечается как непригодный для выводов.**

### 5.2 Раздел «Рынок» — по каждой из 20 пар

| Метрика |
|---|
| Спред USDC: медиана, 25-й и 75-й процентиль, доля времени выше 0.05% |
| Спред USD того же актива: те же величины |
| Отношение спредов USDC/USD |
| Базис USDC/USD: медиана, дисперсия, максимальное отклонение |
| Поток: сделок в сутки, объём в сутки, распределение размеров сделок |
| Профиль по часам суток и дням недели |
| Глубина на лучшей цене и суммарная на 5 уровнях |

### 5.3 Раздел «Симуляция» — по каждой паре и в целом

P&L с разложением на три компоненты; число исполнений и доля от общего потока; **markout на 0/10/60/300 с**; максимальная просадка; распределение времени удержания инвентаря; доля времени с полным инвентарём; число перевыставлений в сутки против лимита запросов; сравнение с обоими контролями; результат при каждом уровне комиссии.

### 5.4 Раздел «Вердикт»

Прямые ответы на вопросы, ради которых строился стенд:

1. Превышает ли реализованный захват неблагоприятный отбор? Число, не мнение.
2. Какая доля P&L объясняется спредом, а какая — направленным дрейфом инвентаря?
3. Превосходит ли стратегия buy & hold на том же инвентаре?
4. Превосходит ли она случайное котирование?
5. При какой maker-комиссии результат обращается в ноль?
6. Реализуема ли требуемая частота перевыставлений в рамках лимитов API?
7. Какие пары из 20 проходят по спреду и потоку одновременно?
8. Отличается ли поведение в выходные и ночью настолько, чтобы менять режим работы?

### 5.5 Kill-критерии стратегии

Формулируются **до** первого прогона, чтобы результат нельзя было переинтерпретировать:

| Условие | Вывод |
|---|---|
| `half_spread + markout(60с)` не положителен с запасом | направление закрывается |
| Стратегия не превосходит buy & hold | работал направленный дрейф, не спред |
| Стратегия не превосходит случайное котирование | выбор цен не добавляет ценности |
| Результат уходит в минус при maker 0.02% | конструкция держится на промо-тарифе |
| Требуемая частота запросов выше лимита | нереализуемо технически |
| Больше 70% P&L из компоненты `inventory_pnl` | это не маркет-мейкинг, а лонг с накладными |

**О первой строке (правка ТЗ 72 §10).** Раньше здесь стояло «`markout(60 с)` отрицателен».
Это закрывало направление на любом отрицательном числе, тогда как маркет-мейкер и обязан
терять на markout: он покупает ниже середины и продаёт выше неё, а цена после исполнения
в среднем идёт против него. Заработок — разница между захваченной половиной спреда и этой
потерей. Поэтому критерий формулируется на сумме `half_spread + markout(60 с)`, и «с запасом»
означает: положительная сумма обязана перекрывать комиссию и оценённую ошибку измерения,
а не быть просто больше нуля.

## 6. Этап 2 (только после положительного отчёта): форвард и микро-live

Не начинать, пока §5.4 не даст ответы.

**Форвард-режим.** Тот же движок котирования работает на живых данных в реальном времени, но ордера не отправляет — записывает, что выставил бы, и по ленте сделок определяет, исполнилось бы. Смысл: сверка с симулятором на данных, которых симулятор не видел. Расхождение форварда с симуляцией — прямая оценка ошибки модели исполнения.

**Микро-live.** Реальные ордера минимального размера (`min_order_size_quote` = 0.1 USDC позволяет проверку на суммах в единицы долларов). Отвечает на единственный вопрос, недоступный симуляции: **доходит ли поток до нашей заявки или матчится внутри биржи.** Ключевая метрика — доля исполнений, предсказанных моделью, против фактических.

Требования к этому этапу: ключи только из переменных окружения, никогда в конфиге и репозитории; жёсткий лимит суммарной экспозиции в коде, не в конфиге; аварийная остановка по одной команде с отменой всех заявок; полный журнал всех отправленных запросов и ответов.

## 7. Тесты — критерии приёмки

Без этих тестов работа не принимается.

**Модель исполнения:**

- заявка не исполняется, если объём сделок через её цену меньше очереди перед ней;
- заявка исполняется частично, если объёма хватает только на часть;
- заявка вне 5 видимых уровней не исполняется никогда;
- сделка с неопределённым агрессором не вызывает исполнения;
- при одновременном срабатывании обеих сторон в одном окне исполняется только невыгодная нам.

**Синтетические сценарии с известным ответом:**

- **нулевой поток** → ноль исполнений, ноль P&L;
- **строго односторонний поток вниз** → инвентарь упирается в потолок, бид перестаёт выставляться, `spread_capture` мал, `inventory_pnl` отрицателен;
- **идеальный колебательный поток без тренда** → `spread_capture` близок к теоретическому `2*d` на round-trip, `inventory_pnl` около нуля;
- **поток только по лучшей цене со стороны информированного агрессора** → `markout(60с)` отрицателен.

Последний сценарий — главный: он проверяет, что стенд **способен обнаружить** неблагоприятный отбор. Стенд, который не умеет показать отрицательный результат на данных, где он заведомо есть, бесполезен.

**Данные:**

- парсер книги корректно обрабатывает массив `asks` в убывающем порядке;
- инвариант `best_ask > best_bid` проверяется, нарушение логируется;
- пагинация ленты сделок доходит до конца диапазона и не теряет записи на границах страниц;
- снимки с превышением `skew_ms` исключаются из расчёта базиса;
- курс USDC/USD по медиане устойчив к одной аномальной паре — тест с подставленным выбросом.

**Воспроизводимость:** повторный прогон на тех же данных с тем же конфигом даёт побитово тот же результат. Любая случайность — только с фиксированным seed из конфига.

## 8. Чего не делать

| Не делать | Причина |
|---|---|
| Оптимизировать параметры по результату симуляции | подгонка. Параметры задаются из логики до прогона; допустима только проверка чувствительности |
| Добавлять индикаторы и предсказание направления | стенд проверяет захват спреда, а не прогноз. Смешение сделает результат неинтерпретируемым |
| Строить веб-интерфейс, дашборды, графики | на этом этапе нужны числа, а не визуализация |
| Поддерживать другие биржи | преимущество здесь в конкретном тарифе конкретной площадки |
| Хранить торговые ключи | этап 1 их не требует вообще |
| Чинить аномалии данных «на лету» | аномалия должна попасть в журнал и в отчёт, а не быть незаметно исправленной |
| Начинать сбор с мемкоинов | самый широкий спред и самый высокий риск инвентаря. Проверять надо механизм, а не везение |

## 9. Порядок работ

| Этап | Содержание | Результат |
|---|---|---|
| 1 | Коллектор + определение фактических rate limits | процесс, пишущий данные без пропусков |
| 2 | Запуск сбора на 7+ суток | не останавливать ни при каком развитии остальных этапов |
| 3 | Парсер, расчёт курса USDC/USD, тесты данных | проверенный слой данных |
| 4 | Модель исполнения + тесты §7 | ядро, прошедшее синтетические сценарии |
| 5 | Симулятор, разложение P&L, markout | прогоны из §4.7 |
| 6 | Отчёт | ответы на §5.4 |
| 7 | Форвард-режим | только при положительном отчёте |

**Этап 2 запускается первым по календарю и идёт параллельно всему остальному.** Данные книги невосполнимы: каждый день без сбора — потерянный навсегда день наблюдений. Разработка модулей 3–6 ведётся на уже накапливающихся данных.

## 10. Оговорки, которые должны попасть в README

- **maker 0% — вероятно промо** молодой площадки. Конструкция, нежизнеспособная при maker 0.02%, построена на акции, а не на преимуществе. Прогон чувствительности к комиссии — не дополнительный, а основной.
- **Спот-онли означает вынужденный лонг.** Котировать аск можно только в пределах имеющегося инвентаря. Стратегия структурно длинная, и корректный бенчмарк — держание инвентаря, а не ноль.
- **Симуляция не отвечает на вопрос о внутреннем матчинге.** Если широкий спред на USDC-книге держит сама биржа или её контрактный маркет-мейкер, поток может не доходить до наших заявок. Это разрешается только микро-live.
- **Все выводы ограничены собранным периодом.** Неделя данных не описывает поведение в стрессовом режиме рынка.
