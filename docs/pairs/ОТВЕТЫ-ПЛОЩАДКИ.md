# Ответы Revolut X: каталог по 7795 живым отказам

**Короткий ответ на вопрос «нет ли полного списка кодов или подкодов»: НЕТ.**
Различать ответы можно ТОЛЬКО по человеческому тексту `message` — другого
признака площадка не даёт.

## Что говорит сама документация

Официальный машиночитаемый справочник
([revolut-engineering/revolut-x-api](https://github.com/revolut-engineering/revolut-x-api/blob/master/revolut-x-api-for-llm.md))
формулирует это прямо: *«No machine-readable error codes or sub-codes are
documented beyond HTTP status codes and the human-readable message field»*.

Тело ошибки — ровно три поля, и это подтверждается нашими 6148 разобранными
ответами (никаких других полей не встречалось ни разу):

```json
{"error_id": "<uuid>", "message": "<текст>", "timestamp": 1789044428202}
```

⚠️ `error_id` — идентификатор СЛУЧАЯ, а не класса: он уникален для каждого
отказа и для классификации бесполезен.

⚠️ И того хуже: **`PUT /orders/{id}` в документации отсутствует вовсе** — его
нет среди 16 описанных адресов. Ни 422, ни формат 429 не документированы
никак. То есть весь путь замены, на котором держится бот, не описан, и всё
знание о нём — наше собственное, добытое из живых ответов.

## Три грабли, которые видно только из этой таблицы

**1. Под кодом 422 живут ТРИ РАЗНЫХ смысла, и текст — единственное различие.**
Из них `Could not replace order with id` долго считался «временным отказом при
живой заявке». ⚠️ **Опровергнуто 10.09.2026:** восемь таких отказов за 13 секунд,
а заявка в это время исполнилась, и исполнение пропало из учёта навсегда.
Вывод: **судьбу заявки нельзя выводить из текста вообще** — только вопросом
`GET /orders/{id}`. См. `ЗАДАЧИ.md` §A7-bis.

**2. Большинство 429 — не JSON, а HTML.** 564 из ~694: их отдаёт защита
периметра, а не API, и `message` там нет вовсе. Разбор ответа как JSON на них
падает; проверять надо код, а не тело.

**3. `Insufficient balance` не имеет устойчивого формата.** Встречались
`₿0`, `Ξ0.00072`, `0 SOL`, `59.77 ADA`, и просто число без валюты — символ,
код и порядок слов меняются от пары к паре. Разбирать этот текст на числа
нельзя; годится только сам факт отказа.

## Как этим пользоваться

Правило одно и оно следует из отсутствия кодов: **текст годится, чтобы понять
КЛАСС проблемы (деловой отказ / лимит / поломка), но никогда — чтобы вывести
СОСТОЯНИЕ заявки.** Состояние спрашивается у площадки: `GET /orders/{id}` для
одной заявки, `GET /orders/active` для списка.

Каталог пересобирается одной выборкой по журналам:

```sql
SELECT status, response FROM exec_request WHERE status >= 400
```
