# Читатель площадки: учёт заявок без потерь (задача A92, 27.09.2026)

Две беды, которые сюда привели:

1. **теряем исполнения** — прогон 22.09 16:09 → 23.09 15:49 записал 459 заявок с
   исполнением из 465; шесть исполнений площадки ботами не записаны (a −1 лот BTC,
   e −2 лота BTC, d −1 лот ETH, f +1 лот SOL, b +1 лот SOL, у b записан по догадке
   в другое время и по другой цене);
2. **монеты заперты без заявок** (A48/A51) — площадка держит `reserved`, а ни
   одной заявки под него не показывает.

## 1. Что установлено (зонды `--revx-history-probe`, только GET)

### У площадки ЕСТЬ история, запись от 14.09.2026 была ошибкой

Зонд 14.09 перебирал угаданные адреса (`/orders/history`, `/fills`, `/trades/my`)
и записал «истории заявок нет». Документация называет другие:

| адрес | что даёт | годится для |
|---|---|---|
| `GET /api/1.0/trades/private/{SYM-USDC}` | наши сделки: `tid`, `oid`, `s`, `q`, `p`, `tdt`, `im` | **источник правды об исполнениях**: ~470 сделок в сутки на шести ботах, две страницы на пару |
| `GET /api/1.0/orders/historical` | все заявки аккаунта, в т.ч. `previous_order_id` и `client_order_id` | цепочки замен и справки; ⚠️ **фильтр по времени СОЗДАНИЯ** (11 из 11 проверок) — окно «последние N минут» не видит исполнения давно стоящей заявки; каждая замена — отдельная заявка, 60 000 записей покрывают лишь часы. Без `symbols` работает, отдаёт все пары |
| `GET /api/1.0/orders/fills/{id}` | сделки одной заявки | справки |

В сделке нет `client_order_id`, есть `oid`; метку бота даёт один
`GET /orders/{oid}`. Все шесть потерянных исполнений нашлись в ленте сделок с
правильными объёмами, и все шесть — заявки с меткой нашего бота.

### Площадка несогласована в затык — ответ не равен сделанному

Все шесть потерь пришлись на затыки (`venue_stall`: замена дольше 1 с), когда бот
отходит в сторону и снимает заявки. Трассировка по журналам:

| бот | что бот видел | что было на самом деле |
|---|---|---|
| e 22.09 17:20 | `DELETE` → **204** | исполнилась за 37 мс до отмены |
| d 23.09 14:13 | `PUT` → 422, `GET` → 200, `DELETE` → **204** | исполнилась до `PUT` |
| b 22.09 20:02 | `DELETE` → 404, `GET` → 404, через 47 с «new», `DELETE` → **204** | исполнилась через **4 с после** ответа 204 |
| f 23.09 11:26 | `PUT` 1 с → 200, `DELETE` → 404 «нет активной» | была жива, исполнилась через 3 с |
| a 23.09 14:14 | `POST` → 200, через 0.2 с `DELETE` → 404 | исполнилась через 0.6 с |
| e 23.09 14:13 | `PUT`, `GET`, `DELETE` → **404** «заявки нет» | уже исполнилась, запись появилась через 2 с |

🔑 **В затык ни 204 на отмену, ни 404 не окончательны.** Бот принимал их за
окончательные, освобождал слот и больше о заявке не спрашивал. Надёжной в
разобранных случаях оказалась только лента сделок; статус заявки становится
правдой с задержкой, балансы — последними (часы).

### Призрак замены — это утечка резерва, а не спрятанная заявка

Из семи тревог `ghost_replace` прогона:
- **три ложные**: замена отказала по «Not enough funds», наследника не создавала;
- **четыре настоящие**, все в затык `HH:38:32`, одна последовательность:

```
01:38:26.728  PUT → 200 за 140 мс, создана заявка P
01:38:29.727  PUT на P отправлен … площадка висит
01:38:32.329  P стала «cancelled (replaced)»      ← внутри этого же запроса
01:38:32.816  ответ на тот же PUT: 422 «not in NEW state», 3089 мс
```

Параллельных запросов нет (бот шлёт последовательно). Площадка внутри одного
запроса отменила предка, наследника **не создала** — его нет в истории ни по
нашему `client_order_id`, ни по `previous_order_id`, хотя у ложных случаев поиск
по предку находит, — и резерв предка не отпустила. Исполниться такому «наследнику»
нечем: все шесть потерь объяснены другим механизмом, а в A51 итоги после отпуска
сошлись до восьмого знака. **Призрак запирает монеты на 2–32 ч, но деньги не
теряет.** Снять его нечем — идентификатора нет нигде.

## 2. Чьи монеты на счёте

Монеты на счёте не подписаны. Принадлежность — наш учёт:

```
на счёте = Σ претензий ботов (alloc.db) + ничейное
```

Претензия меняется только своими исполнениями, `/claim` и `/release`. Потерянное
исполнение разводит претензию с реальностью — отсюда «претензий больше, чем
монеты» по BTC после прогона. Схема ниже чинит именно этот вход.

## 3. Схема

### 3.1. Читатель (`--revx-venue`, служба `revx-venue`)

Один процесс, только GET, пишет `revx-shared/venue.db` (WAL: один писатель,
читают боты и сводка).

| таблица | откуда | период | что |
|---|---|---|---|
| `trade` | `/trades/private/{пара}` | 2 с по кругу | `tid` (ключ), `oid`, сторона, объём, цена, `tdt`, когда увидели, **бот** |
| `order_info` | `GET /orders/{oid}` | по новым `oid` и по `order_watch` | `client_order_id`, **бот**, статус, исполнено, `created`, `updated`, когда проверили |
| `order_watch` | пишут боты (этап 3) | — | «следи за заявкой»: `oid`, бот, причина, с какого момента |
| `live_order` | `/orders/active` | 1 с | последний снимок + время НАЧАЛА запроса (`snapshot`) |
| `balance` | `/balances` | 5 с | total, reserved, available |
| `reserve_gap` | вычисляет | 5 с | по монете `reserved − Σ видимых заявок`, с какого момента |
| `heartbeat` | сам | каждый цикл | время последнего УСПЕШНОГО цикла, ошибки, 429, последняя ошибка |
| `shadow_diff` | сверка с журналами ботов | 60 с | сделка у площадки, не записанная ботом (или записанная не так) |

Бюджет ≈ 60 (`active`) + 90 (сделки) + 12 (балансы) + до 60 (`orders/{id}`) ≈
**220 GET/мин** — меньше, чем боты тратят сейчас сами (только `/orders/{id}` было
~227/мин).

### 3.2. Бот: запись у себя, чтение из `venue.db`

`POST`/`PUT`/`DELETE` остаются в боте и пишутся в его журнал до отправки. Своих
GET у бота нет.

### 3.3. Слот заявки

```
ПУСТО ──POST──► ОТПРАВЛЕНА ──200 быстро──► ЖИВАЯ ──PUT 200 быстро──► ЖИВАЯ (новый oid)
                    │                        │
                    │ неоднозначно            │ неоднозначно / любой DELETE
                    ▼                        ▼
               ПОД ВОПРОСОМ ◄───────────────────
                    │ окончательный статус + тишина в ленте N с
                    ▼
               ПОДТВЕРЖДЕНА ──► учёт сделок из trade ──► ПУСТО
```

- **неоднозначный ответ** — всё, кроме быстрого 200 на `POST`/`PUT`: 422, 404,
  5xx, 429 на запись, таймаут, ответ дольше 1 с, **любой ответ на `DELETE`**;
- **под вопросом** — заявка уходит в `order_watch`, бот к ней больше не
  обращается, слот занят;
- **подтверждена** — (1) статус окончательный, (2) после него N с без новых
  сделок по `oid`, (3) проверка отправлена позже нашего последнего запроса по
  заявке. N меряется в тени; стартовое 10 с (b: сделка через 4 с после 204);
- **свежесть**: «заявки нет в книге» — только по снимку `live_order`, начатому
  после нашего последнего `POST`/`PUT`;
- **в затык отмена остаётся** — иначе устаревшую котировку исполнят по плохой
  цене. Меняется не действие, а то, как читается ответ;
- **422 на замену в затык**: предок `cancelled (replaced)`, наследника нет —
  у бота подозрение на запертое (сторона, размер).

### 3.4. Исполнения — только из `trade`

По `tid` (колонка в `exec_fill`, дубли исключены), цена и объём из сделки, реестр
обновляется там же. Сделка по «отменённой» заявке записывается всё равно. При
перезапуске бот догоняет ленту с последнего записанного `tid`.

### 3.5. Что можно продать и купить

```
позиция         = Σ своих сделок                          ← скос и потолок от неё
запертое        = подтверждённые подозрения (3.6)
в книге         = Σ остатков своих ЖИВЫХ заявок по стороне
под вопросом    = Σ размеров своих заявок ПОД ВОПРОСОМ по стороне

можно продать   = min( позиция − запертое − в книге − под вопросом,
                       available монеты на счёте )
можно купить на = min( касса − запертый USDC − в книге − под вопросом,
                       available USDC на счёте )
```

`available` один не годится — счёт общий, в нём монеты соседа и ничейные. Второе
слагаемое `min` — страховка: даже при ошибке учёта бот не продаст больше, чем
реально свободно. Запертое **своё, но недоступное**: в позиции и скосе оно есть
(монеты вернутся, докупать незачем), в «можно продать» его нет. Это заменяет
паузу A51: бот торгует свободной частью и при этом не кренится в покупку, из-за
чего в A51 паузу и выбрали.

### 3.6. Запертое

- подозрение заводит бот (3.3);
- подтверждение — `reserve_gap` по монете не меньше суммы подозрений;
- отпуск — `reserve_gap` упал: подозрение снимается, позиция не меняется;
- разница без хозяина — тревога, никому не приписывается.

### 3.7. Если читатель упал

- сердцебиение старше 5 с — боты не ставят и не заменяют, отмена разрешена всегда;
- старше 60 с — снимают своё, отмены сразу «под вопросом»;
- **сводка `revx-info` будит** 💀, когда последний успешный цикл читателя старше
  минуты, и пишет 🟢, когда ожил. В `/all` — строка состояния читателя.

### 3.8. Что уходит из бота (этап 4)

Запись по двум уликам (`inferred_fill`, `heir_gap_too_big`), очередь
`unknownFate`, свои `GET /orders/{id}` и `/orders/active`, восстановление при
старте по хвостам запросов, пауза по запертому резерву.

## 4. Этапы

1. **Читатель в тени** — пишет `venue.db`, боты его не читают. Сверка с
   журналами ботов (`shadow_diff`), замер N и задержек. Тревога в сводку при
   падении. ← **в работе с 27.09.2026**
2. **Исполнения из `trade`** — бот записывает по `tid`, старый путь параллельно;
   совпадение проверяется дублями по `oid`.
3. **Слоты и формулы** 3.3/3.5; стенду (`SimVenue`) — режим «несогласованной
   площадки»: задержанный статус, 204 с последующим исполнением, 404 на свежей
   заявке, 422 с отменённым предком.
4. **Удаление старых путей** (3.8).

## 5. Открытые вопросы (меряются на этапе 1)

- задержка появления сделки в `/trades/private` от `tdt`;
- задержка окончательного статуса в `GET /orders/{id}` после затыка;
- бывает ли сделка после окончательного `cancelled` (а не только после ответа 204);
- сходится ли `reserve_gap` с суммой подозрений ботов.
