**В одну строку:** отдельный процесс `revx-hedge` на bot-arm. Он читает запас бота
`b` из общей базы читателя площадки (`venue.db`), а не из памяти бота. На Kraken
держит шорт `PF_SOLUSD`: заявки post-only в касание, через `T` секунд добивка
тейкером. Всё, что он делает, пишется в свой журнал. Жёсткие пределы стоят в коде;
любая неясность — заморозка и тревога, а не действие вслепую.

## 2. Откуда запас

**Источник — исполнения бота, а не его память.** С этапа 2 читателя площадки
(`ЧИТАТЕЛЬ-ПЛОЩАДКИ.md`) исполнения ботов пишутся по ленте сделок площадки
(`trade` в `venue.db`, метка бота по `client_order_id`). Запас бота `b` для хеджа:

```
запас_b(t) = затравка_b + Σ сделок b из trade до t      (покупка +, продажа −)
```

**Сверка раз в `N` = 5 минут:** запас из ленты против позиции в журнале бота
(`exec_state.position`) и против остатка монеты на счёте Revolut (`balance` в
`venue.db`) за вычетом чужих претензий (`alloc.db`). Расхождение больше половины
лота дольше двух сверок — **стоп хеджа** (заморозка, §6).

⚠️ **Пилот начинается только после этапа 2 читателя.** Сегодня исполнения бота
теряются в затык (6 из 465 за сутки 22–23.09), и хедж, построенный на таком запасе,
держал бы позицию против несуществующих монет.

## 3. API Kraken

| действие | адрес | что проверить до кода |
|---|---|---|
| заявка post-only | `POST /derivatives/api/v3/sendorder`, `orderType=post`, свой `cliOrdId` | формат ответа при отказе post-only (цена пересекла книгу) |
| изменение цены | `POST /api/v3/editorder` (по `orderId` или `cliOrdId`) | сохраняется ли место в очереди при сдвиге |
| отмена | `POST /api/v3/cancelorder` (по `cliOrdId`), `cancelallorders` | ответ на отмену уже исполненной |
| открытые заявки | `GET /api/v3/openorders` | |
| позиции | `GET /api/v3/openpositions` | знак и единицы у `PF_` |
| исполнения | `GET /api/v3/fills` — `fillType` (`maker`/`taker`) | глубина истории |
| журнал счёта | `GET /api/history/v3/account-log` — фандинг, комиссии, реализованный результат | формат записей фандинга |
| инструмент | `GET /api/v3/instruments` — шаг контракта, тик цены | сверить шаг 0.01 SOL (163) |

- **Идентификаторы.** Каждая заявка — свой `cliOrdId` = метка пилота + номер. Повтор
  после сбоя сначала спрашивает `openorders`/`fills` по этому `cliOrdId` и только
  потом ставит заново. Урок Revolut (`ЧИТАТЕЛЬ-ПЛОЩАДКИ.md`): ответ, пришедший в
  затык, не окончателен, и судьбу заявки надо выяснять чтением.
- **Лимиты запросов Kraken** — бюджет «стоимостей» на 10 секунд для
  `/derivatives` и отдельный для `/history`. Числа сверить с документацией до кода.
  По нашему темпу (до 10–40 заявок в сутки, опрос раз в 5–10 с) до лимита далеко.
- **Клиент.** Существующий `KrakenFuturesExchange` (S5) умеет только рыночные
  заявки, позиции, баланс и `fills`. Нужны `orderType=post`, `cliOrdId`,
  `editorder`, `cancelorder`, `openorders`, `account-log`. Расширять его, а не
  писать второй: подпись (`KrakenSigner`) и ретраи уже проверены живьём на S5.

## 6. Сбои

| что | реакция |
|---|---|
| нет свежих данных о запасе дольше 5 мин (читатель упал, лента молчит) | **заморозить хедж** (не ставить и не менять заявок) и тревога. Закрывать вслепую нельзя: если бот жив, это открыть спот без страховки (192) |

| расхождение сверки запаса (§2) | стоп |
| бот `b` ушёл в темноту по бюджету | правило «перед темнотой» (если выбрано в §9), дальше — держать |

## 7. Жёсткие пределы в коде

- `|запас + хедж| ≤ полоса + шаг` — иначе стоп, а не перевешивание;
- `|хедж| ≤ потолок запаса b` (0.132 SOL при нынешних настройках);
- размер заявки `≤ потолок запаса`;
- не больше `K` = 6 заявок в минуту и 200 в сутки;
- использованный залог `≤ 50%` — стоп;
- выключатель — `/hedge_stop`, и он же при любом из стопов пилота (191 IV).

## 9. Настройка хеджа — из прогона части II

По прогону `--revx-hedge-grid` (док. 194), правило выбора записано до прогона:

- **правило:** выравнивать к нулю **раз в 60 минут** (если `|запас + хедж|` не меньше
  шага), заявка post-only в касание, **ждать 120 с**, потом тейкером;
- **«до нуля перед темнотой» — не нужно**: на двух окнах разница в пределах шума;
- **контрольное число пилота — мейкерская доля ≥ 56%** (порог, ниже которого хедж
  SOL на растущем окне уходит в минус; оценка снизу по 163 — 76%);
- ожидаемый выигрыш — доли цента на бот-сутки, `t` ≈ 0.1–0.5: пилот проверяет
  механику, а не доход (191).

## 10. Бухгалтерия (191 V)

Таблица `hedge_fill` (исполнения Kraken: время, сторона, цена, объём, комиссия,
maker/taker, `cliOrdId`), `hedge_funding` (из `account-log`), `hedge_daily`
(сутки UTC). Для обеих ног — одна опорная цена SOL на 00:00 UTC (середина книги
Revolut) и курс USDC/USD на тот же момент (прямая книга `USDC-USD` из
сборщика).

Ежедневно в 00:05 UTC:
```
Revolut: захват + цена запаса + бета      (по журналу b, как --revx-carry)
Kraken:  переоценка + реализованный − комиссии + фандинг   (по account-log)
сверка:  нога хеджа ≈ −(переноска запаса) с поправкой на полосу, шаг, базис
```
Зазор больше $0.01 — строка в сводке, больше $0.05 без объяснения — стоп (191 IV).

## 11. Ключи и счёт Kraken

**Состояние на 27.09.2026 (владелец):** ключ Kraken есть — тот, что у S5, на micro
(`~/s5/kraken/keys.txt`, права General = Full, Withdrawal = No, то есть без вывода —
требование 192 выполнено). Бюджет на счёте есть.

- ⚠️ **Счёт общий с S5 (`s5-live` на micro работает с того же счёта).** Kraken
  НЕТТИРУЕТ позиции по контракту: если S5 откроет шорт `PF_SOLUSD` (разлок SOL), его
  позиция сложится с хеджем, и `openpositions` покажет одну сумму. Отсюда правила:
  - хедж ведёт СВОЮ позицию по своим исполнениям (`cliOrdId` с меткой хеджа), а не
    по `openpositions`; сверка — «позиция счёта = своя + позиция S5 из `s5.db`»;
  - если у S5 есть открытая позиция по SOL — хедж не стартует и не наращивает шорт,
    только тревога (одна программа не должна трогать позицию другой);
  - стоп по пределу у хеджа — только `reduceOnly` и только на свой размер;
  - ⚠️ `cancelallorders` по символу снял бы и стопы S5 (`placeStopBuy`) — хеджу
    пользоваться только поимённой отменой по своему `cliOrdId`.
- **Где ключ.** Хедж по проекту живёт на bot-arm, рядом с `venue.db`. Два пути, решает
  владелец: (а) **отдельный ключ того же счёта** для хеджа — можно отозвать, не трогая
  S5 (предпочтительно); (б) копия ключа S5 на bot-arm в `/etc/revx-hedge.env`
  (права 600, только root/ubuntu). В репозиторий и журналы — никогда.
- Revolut: хедж на Revolut ничего не ставит и ключа Revolut не получает.

## 13. Контроль

`f` чистым контролем для `b` не годится (193): три уровня против одного, другой лот
и другая доля бюджета. Два пути, решает владелец:
- **перевести `f` в форму `b`** (один уровень, тот же лот и предел 100) на время
  пилота — тогда `f` честный контроль на том же рынке;
- **или** сравнивать живую ногу `b` с тем же хеджем, наложенным прибором на ту же
  траекторию `b` (критерий 2 пилота из 191 IV).
