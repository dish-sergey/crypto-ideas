## 1. Разведка живого API 19.08.2026 — что подтвердилось и что изменилось

Проверено запросами с локальной машины (`region=EEA` принимается, авторизация не нужна).

**Подтвердилось:**

- `asks` действительно приходят **в убывающем порядке**: в снимке ETH/USDC `asks[0]=2101.00`,
  а лучший аск — `asks[4]=2097.13`. Наивное `asks[0]` дало бы спред 0.52% вместо 0.335%.
  Требование ТЗ §3.2 о явной сортировке и инварианте — обязательно, ошибка реальна.
- Ответ книги содержит `metadata.timestamp` (мс, серверное время) — это **третье** время
  в дополнение к `t_request_sent` / `t_response_received` из ТЗ §3.3, пишем и его.
- Лента сделок отдаёт `metadata.next_cursor` (base64 `date=…;id=…`) — пагинация как в ТЗ §3.2.
- `min_order_size_quote = 0.1` подтверждается; спецификация пары даёт `base_step`, `quote_step`,
  `min/max_order_size`, `status`, `slippage`.

**Разошлось с ТЗ / док. 62 — учесть в реализации:**

| Наблюдение 19.08.2026 | Что меняет |
|---|---|
| USDC-пар **23**, не 20 (добавились JUP, XRP, XLM), всего пар 385 | вселенная = **46 символов**, а не 40 → бюджет запросов ×1.15. Список тянуть динамически (ТЗ §3.4 это уже требует) |
| USD-аналог есть **у всех 23** USDC-пар | пар без опоры нет, отдельная ветка не нужна |
| `/configuration/pairs` отдаёт **объект-словарь**, ключ `"ETH/USDC"` (через слэш), а не массив с полем `data` | парсер: `Map<String, PairSpec>`; в пути книги символ через **дефис** (`ETH-USDC`) — два разных формата в одном API |
| Лента сделок **отдаёт `side`** (`buy`/`sell`) | правило вывода агрессора из ТЗ §4.3 нужно не как основной путь, а как **валидатор**: сверяем поле `side` с правилом «ближе к аску/биду», долю расхождений — в отчёт. Семантика поля (агрессор или сторона мейкера) не документирована — проверяем эмпирически по книге |
| Поток по BTC/USDC: 100 сделок за **0.72 ч** (в док. 62 было 100 за 9.03 ч) | оценка «≥266 сделок/день» — сильно нижняя граница; пагинация обязательна, иначе поток занижается в разы |
| Спред ETH/USDC в момент замера **0.335%** (2090.13 / 2097.13) | подтверждает порядок величины из док. 62 (0.239%), но распределение всё равно неизвестно — за этим и собираем |
| Цены сдвинулись (BTC/USDC ≈ 68.5k против 63.2k в док. 62) | числа док. 62 — снимок момента, для отчёта опорой не служат |

Ни один из этих фактов не ломает гипотезу; они меняют парсеры, размер вселенной и
приоритет пагинации.

## 2. Что переиспользуем из crypto-ideas, а что нет

**Переиспользуем:**

- `core/Db` — SQLite-writer с WAL, upsert/batch/query. Идемпотентность (принцип 2 CLAUDE.md)
  ложится на естественные PK: `(symbol, t_sent_ms)` у книги, `trade_id` у сделок.
- `cli/CliRunner` + `CliMode` — новые режимы `--revx-collect`, `--revx-probe-limits`,
  `--revx-sim`, `--revx-report`.
- Сборку (`bootJar`) и схему деплоя на micro (systemd-юнит по образцу `crypto-data`).

**НЕ переиспользуем `core/ApiClient` — и это принципиально.**
Его троттлинг (`throttle(host)`) сериализует **все** запросы к одному хосту с
минимальным интервалом (по умолчанию 350 мс) и делает это блокирующим `sleep` в
вызывающем потоке. Для ТЗ §3.3 нужно ровно обратное: **две ноги пары (USDC и USD)
должны уходить одновременно**, чтобы `skew_ms` был меньше 250 мс. С ApiClient
минимальный skew был бы ≥350 мс — то есть базис нельзя было бы измерить вообще.

Поэтому для стенда — свой `revx/RevxHttp`:
- `HttpClient.sendAsync` + виртуальные потоки, пары ног отправляются одним батчем;
- **глобальный token-bucket** (req/s из конфига) вместо пер-хостового интервала —
  ограничивает суммарный темп, но допускает одновременность внутри батча;
- экспоненциальный backoff **с джиттером** на 429/5xx (в ApiClient джиттера нет);
- счётчик 429 и общих запросов → метрика прогона (ТЗ §3.2: >1% 429 = отчёт неполный).

**Отдельный файл БД `data/revx.db`, не `crypto.db`.** Две причины: (1) объём —
46 символов × 17 280 снимков/сут ≈ **0.8 млн строк/сут**, ~1–1.5 ГБ за неделю;
(2) `crypto.db` непрерывно реплицируется Litestream в B2 (free-лимит 10 ГБ, уже
ловили распухание скрытых версий — см. `deploy/SERVERS.md`). **revx.db в Litestream
не добавлять.** Технически: `Db` сейчас жёстко берёт `${data.db-path}` и
`schema.sql` из classpath — нужен маленький рефактор (конструктор с путём и именем
schema-ресурса), второй бин `revxDb` со своим `schema-revx.sql`.

## 3. Состав модуля

```
org.home.data.revx
  RevxConfig              конфиг (configs/revx.yaml): вселенная, частоты, лимиты, параметры стратегии
  RevxHttp                async-GET, token-bucket, backoff+jitter, счётчики 429/ошибок
  PairsCatalog            /configuration/pairs (Map-формат), суточное обновление, появление/исчезновение пар
  BookCollector           параллельные ноги USDC+USD, сортировка, инвариант, skew_ms, флаги
  TradesCollector         /trades/all с пагинацией по cursor, докачка окна после простоя
  RateLimitProbe          --revx-probe-limits: медленный рост частоты до устойчивого 429
  AnomalyLog              журнал аномалий (не «чинить на лету» — ТЗ §8)
  Health                  heartbeat-файл + таблица аптайма
  sim/
    FairPrice             медиана implied_i по неммемкоин-парам, порог разброса → пауза котирования
    Quoter                отступ d, скос по инвентарю, потолок, post-only, порог перевыставления
    ExecutionModel        queue_ahead, частичные исполнения, консервативность при неоднозначности
    Pnl                   spread_capture + inventory_pnl − fees (разложение обязано сходиться)
    Markout               Δ ∈ {0, 10с, 60с, 300с} по опорной цене USD
    Controls              buy&hold и случайные котировки
    RunRegistry           git-хэш + полный конфиг + диапазон данных + версия модели → запись прогона
  report/
    MarkdownReport        разделы §5.1–5.5 ТЗ
```

### Схема `data/revx.db` (черновик)

| Таблица | PK | Смысл |
|---|---|---|
| `revx_pair` | `symbol` | спецификация пары + `first_seen_ms` / `last_seen_ms` (появление и исчезновение) |
| `revx_book` | `(symbol, t_sent_ms)` | `snap_id` (общий у двух ног), `t_sent_ms`, `t_recv_ms`, `server_ts_ms`, `bp1..bp5/bq1..bq5/ap1..ap5/aq1..aq5`, `n_bid`, `n_ask`, `skew_ms`, `flags` |
| `revx_trade` | `trade_id` | `symbol`, `ts_ms`, `price`, `qty`, `side`, `ingest_ms` |
| `revx_anomaly` | `(ts_ms, symbol, kind)` | нарушение инварианта, порядок уровней, skew выше порога, 429 |
| `revx_uptime` | `(minute_ms)` | минутный аптайм по каждому потоку → §5.1 |
| `revx_run` | `run_id` | git-хэш, конфиг, диапазон, версия модели, результат |
| `revx_fill`, `revx_run_metric` | | исполнения и метрики прогона |

Два времени (принцип 1 CLAUDE.md) соблюдаются буквально: событие — `server_ts_ms`
(книга) или `ts_ms` (сделка), `available_at` — `t_recv_ms` / `ingest_ms`. Симулятор
читает **только** по `available_at` — это же и запрет ТЗ §4.6 п.4 на будущие данные.

### Бюджет запросов — упёрлись сразу же (ИЗМЕРЕНО 19.08.2026)

`--revx-probe-limits`, ступени 0.5 → 3 req/s по 30 с, ротация 8 эндпоинтов:

| Темп | Запросов | ok | 429 | Вердикт |
|---|---|---|---|---|
| 0.5 req/s | 15 | 15 | 0 | чисто |
| 0.75 req/s | 23 | 22 | 1 (4.3%) | не подтвердилось на повторе → чисто |
| 1.0 req/s | 30 | 28 | 2 (6.7%) | не подтвердилось на повторе → чисто |
| **1.25 req/s** | 38 | 29 | **9 (23.7%)** | подтвердилось (18.4%) → **устойчивый 429** |

**Лимит глобальный по IP, а не пер-эндпоинтный.** Проверено отдельно: 20 запросов
подряд к одному эндпоинту по 1 req/s — ноль 429; те же 2 req/s, размазанные по 8
разным эндпоинтам, — 40% 429, равномерно по всем восьми. Разносить нагрузку по
символам бессмысленно.

**В 429 приходит `Retry-After` в миллисекундах** (375, 531, 919, 107 — при том что
следующий запрос проходит через секунду), вопреки HTTP-спеке, где это секунды.
Клиент слушает заголовок; значения ≤60 на всякий случай трактуются как секунды.
На подтверждённой перегрузке прилетало и `Retry-After: 27000` — похоже на растущий
штраф, ещё одна причина не упираться в потолок.

**Уточнение по итогам шага 2: ограничен не темп, а ИНТЕРВАЛ между запросами.**
Два запроса встык (две ноги пары параллельно или одна сразу за другой) дают 429 на
втором — при паузе между парами 2.5, 4 и 6 секунд результат один и тот же, ровно
50% отказов. Значит требование ТЗ §3.3 «обе ноги одновременно, skew < 250 мс» с
одного IP **недостижимо в принципе**. Ноги берутся последовательно, измеренный
skew: p50 = 1250 мс, p95 = 1278, max = 1605 (296 снимков). Наведённый шум для
ETH/BTC — порядка 0.01% против базиса 0.08% и спреда 0.24%, то есть измерению не
мешает; порядок ног чередуется от снимка к снимку, чтобы сдвиг не был односторонним.

**Что это меняет.** Рабочий потолок — **0.8 req/s** (запас 20% от чистой ступени),
и это на всё: книги, сделки, каталог. Полный обход 46 ног = **58 секунд**. Опрос
всей вселенной раз в 5 с, как требует ТЗ §3.4, с одного адреса невозможен —
в 5-секундное окно влезают 4 ноги, то есть **две пары**. Ярус фиксируется в конфиге
и попадает в запись прогона: частота снимков определяет грубость модели исполнения,
это не свободный параметр.

Отдельно: тот же лимит — верхняя граница и для **торговых** запросов. ТЗ §5.4 п.6
(«реализуема ли требуемая частота перевыставлений») получил первый ответ ещё до
симулятора: перевыставление стоит запроса, а запросов около одного в секунду на всё.

### Переход на авторизованный API — 19.08.2026, вечер

Публичные лимиты обошлись не прокси на втором адресе (это был бы серый угол ToS
и всего двукратный выигрыш), а **ключом API**: авторизованные эндпоинты рыночных
данных дают 100 req/с и 1000/мин против 1/с. Прирост стократный и легальный.

| Что | Публично | С ключом |
|---|---|---|
| Темп | 0.8 req/s | 12 req/s (лимит 1000/мин) |
| Опрос книг | ярусы, ETH/BTC раз в 10 с | **все 23 пары раз в 5 с** (ТЗ §3.4 выполнен) |
| skew между ногами | 1250 мс | **4.8 мс в среднем, максимум 93** (ТЗ §3.3 выполнен) |
| Ноги | последовательно | залпом |

Что вскрылось при переходе (всё поймано на живых данных, не в теории):

1. **Схема ответа у авторизованных эндпоинтов другая** — `p`/`q`/`no` вместо
   `price`/`quantity`/`count`. Парсер молча выдавал пустые книги, и снимки не
   писались вовсе. Теперь понимает обе схемы, на каждую есть тест.
2. **Символ сделок — в пути** (`/api/1.0/trades/all/{symbol}`), а не в параметрах.
   Старый адрес отвечает `401`, что выглядит как проблема подписи.
3. **Id сделки без дефисов** против UUID публичного пути — одна сделка легла бы
   в базу дважды. Идентификаторы нормализуются, старые строки мигрированы.
4. **Узкое место — не лимит, а задержка ответа.** При 12 req/s фактически шло

### Шаг 5: ядро исполнения и то, что показал первый же строгий тест

Модель исполнения (`sim/ExecutionModel`) сделана по ТЗ §4.3 и везде выбирает
вариант против нас: очередь не уменьшается от чужих отмен, сделка с неизвестным
агрессором ничего не исполняет, заявка вне пяти видимых уровней не исполняется
никогда, а при срабатывании обеих сторон в одном окне остаётся только невыгодная.

Разложение P&L (`sim/PnlBook`) сходится **тождественно**, а не по договорённости:

```
total = Σ s·q·(f_T − p) = Σ s·q·(f_i − p) + Σ s·q·(f_T − f_i) = spread_capture + inventory_pnl
```

Первая версия сценарных тестов прошла с первого раза — и это было подозрительно.
Ужесточение до точных чисел вместо «больше нуля» сразу поймало содержательное:
в сценарии с информированным потоком исполнение случалось **ровно одно** вместо
ожидаемых пяти. Дефекта в модели не оказалось — так работает скос: после первой
покупки бид уходит вниз, и поток, печатающий ровно по прежней цене, перестаёт нас
задевать. Сценарий был неверен, а не код: информированный агрессор сметает уровень
глубже, а не печатает по нему. После правки сценарий даёт то, ради чего он и нужен —
**markout(60с) отрицателен и хуже мгновенного**, то есть стенд способен показать
неблагоприятный отбор там, где он заведомо есть (ТЗ §7).

Побочный вывод на будущее: «больше нуля» в тестах симулятора почти ничего не
проверяет. Ожидаемые числа надо выписывать заранее и целиком.

### Шаг 6: первые прогоны на живых данных — сработали ВСЕ kill-критерии

Окно 14 часов (19–20.08.2026), пары BTC/USDC и ETH/USDC, параметры из конфига,
заданные до прогона. Оговорка сразу: неделя данных ещё не набрана, окно короткое
и захватывает рост BTC — это **не окончательный вердикт**, но и не обнадёживающее
начало.

**BTC/USDC** — 10 020 окон, 343 исполнения, котирование доступно 99.8% времени:

| Показатель | Значение | Что это значит |
|---|---|---|
| Total | **+290.9 USDC** | эквити красивая |
| spread_capture | 47.7 (16%) | а вот это — вся «работа мейкера» |
| inventory_pnl | **243.3 (84%)** | остальное принёс рост BTC |
| markout(0 с / 60 с / 300 с) | +0.139 / **−0.072** / **−0.436** | учебник неблагоприятного отбора |
| Buy & hold на том же инвентаре | 246.2 | стратегия выше всего на 18% |
| Случайные котировки | 242.7 | выбор цен даёт всего +20% |
| Перевыставлений в сутки | **21 365** | при лимите площадки 1000 постановок |

**ETH/USDC** — 32 исполнения, котирование выключено 65.5% времени (широкая опора):
total +0.31 против buy & hold 2.45 и случайных котировок 0.87 — **оба контроля
проиграны**; при maker 0.02% результат уходит в минус (−0.11).

**Сверка с kill-критериями ТЗ §5.5** — сработали все шесть, каждый хотя бы на одной паре:

| Критерий | Статус |
|---|---|
| markout(60 с) в среднем отрицателен | **сработал** (BTC: −0.072) |
| Не превосходит buy & hold | **сработал** (ETH) |
| Не превосходит случайные котировки | **сработал** (ETH) |
| Минус при maker 0.02% | **сработал** (ETH: −0.11; BTC пока держится) |
| Частота запросов выше лимита | **условный** — см. разбор ниже: через `replace` влезаем, запас 1.7× |
| Больше 70% P&L из inventory_pnl | **сработал** (BTC: 84%) |

Это ровно тот исход, который ТЗ §0 предсказывало как типичный, только наоборот:
не «красивая эквити от ошибки в модели», а красивая эквити при честной модели,
которая тут же объясняет, что прибыль пришла из роста рынка, а не из спреда.

**Три вещи, которые надо проверить прежде, чем делать вывод:**

1. **Доля потока 34.5%** — мы забираем треть рыночного объёма фиксированным
   размером 0.05 BTC. Модель не учитывает ни влияния на рынок, ни реакции
   конкурентов: в реальности такое присутствие изменило бы книгу. Верхняя граница,
   а не прогноз.
2. **Лестница отступа ведёт себя не как у мейкера**: total растёт с отступом
   (0.02% → 201, 0.06% → 262, 0.10% → 406) при падении числа исполнений. Для
   захвата спреда это нормально, но здесь это скорее подтверждает, что прибыль —
   от инвентаря: шире отступ → дешевле вход → больше переоценки на растущем рынке.
3. **Лимиты ордеров — уточнено 20.08.2026 по документации** (страница
   `developer.revolut.com/docs/x-api/place-order`):

   | Операция | Лимит |
   |---|---|
   | `POST /orders` (поставить) | 10/с и **1000/сутки** |
   | `PUT /orders/{id}` (заменить) | 10/с, суточного лимита нет |
   | `DELETE /orders/{id}` (отменить) | 100/с и 1000/минуту |

   Первоначальный вывод «не влезаем» был поспешным. 21 365 перевыставлений в сутки —
   это **замены** (0.25/с при разрешённых 10). Суточный лимит в 1000 тратится только
   на СОЗДАНИЕ заявки, то есть после каждого исполнения: при 343 исполнениях за 14 ч
   это ≈590 постановок в сутки. Влезаем с запасом всего 1.7× — вдвое более активный
   рынок упирается в лимит.

   Проверить эмпирически сейчас нельзя: ключ выпущен только на чтение и ордера
   отправлять не может. Вопрос закрывается на этапе микро-live с торговым ключом.
   **Следствие для реализации:** перевыставление обязано идти через `replace`;
   схема «отменить и поставить заново» упирается в лимит уже на текущей активности.
